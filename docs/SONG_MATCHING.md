# 楽曲の照合（コメントの表記 → DB の楽曲）

コメントから取り出した「曲名 / アーティスト」が、DB のどの楽曲を指すのかを決める部分。
実装は `pkg/songmatch`（キーの計算）と `internal/service/song_match_service.go`（判定）。

## 何が問題だったか

以前は `songs` の `(name, original_artist)` 逐字一致だけで判定していた。
そのため次のような表記ゆれがすべて「DB に無い曲」と判定されていた。

| コメント側の表記 | DB の表記 | 外れた理由 |
|---|---|---|
| 少女レイ / みきとP feat. 初音ミク | 少女レイ / みきとP | ボーカル名のクレジット |
| ブレインロット / 東京真中 feat. 重音テト | ブレインロット / 東京真中 | 同上 |
| 私の彼はパイロット / ランカ・リー(中島愛) | 私の彼はパイロット / ランカ・リー=中島愛 | 区切り記号の流儀 |
| ZIGG-ZAGG / Junky(1Chorus) | ZIGG-ZAGG (feat. 初音ミク) / Junky | 両側に別々のノイズ |
| ひこうき雲 / 松任谷由実 | ひこうき雲 / 荒井由実 | **同一人物の別名義** |

そして外れた分は `findOrCreateSong` が新曲として登録していた。
つまり照合漏れがそのまま近似重複になり、次からはさらに当たらなくなる。
**放っておくと悪化する種類の不具合**だった点が重要で、単なる精度の話ではない。

## 設計の柱

### 1. 曲名が強いキー、アーティストは検証用

実測（820 曲）:

| 指標 | 値 |
|---|---|
| 曲名キーの衝突 | **3 組**（`惑星ループ` `オレンジ` `翼をください`。いずれも同名異曲） |
| `original_artist` にクレジット記号を含む | **97 件（12%）** |

アーティスト欄は iTunes 由来のクレジット文字列で、こういう値が普通に入っている。

```
スペシャルウィーク (CV. 和氣あず未), サイレンススズカ (CV. 高野麻里佳) & ...
桜高軽音部 [平沢唯・秋山澪・田井中律・琴吹紬(CV:豊崎愛生、日笠陽子、佐藤聡美、寿美菜子)]
```

逐字一致を要求してよい品質ではない。そこで曲名キーで引いてから、
アーティストは**トークン集合**として突き合わせ、一致条件ではなく絞り込み条件に降格させた。

### 2. 迷ったら残す（括弧の中身）

曲名の括弧を素朴に全部落とすと衝突が 3 組 → **13 組**に増える。中身はこういうものだった。

```
モザイクロール (Reloaded)      vs  モザイクロール          ← 別録音。潰してはいけない
Starry night (instrumental)   vs  Starry night          ← 同上
さくら(独唱)                   vs  さくら                 ← 曲名の一部
ZIGG-ZAGG (feat. 初音ミク)     vs  ZIGG-ZAGG             ← これは落としてよい
```

そこで括弧の中身は**既知の語だけ**を消す（`pkg/songmatch` の `styleWords`）。

- 消す＝演奏方法：`acoustic` `piano` `弾き語り` `アカペラ` `short` `full` `1chorus` `tv size` …
- 残す＝別音源または曲名の一部：`remix` `instrumental` `reloaded` `cover` `live` `独唱` …
- 判断がつかないものは**残す**

取りこぼしは下位ティアに落ちて人が拾えるが、誤一致は黙ってデータを壊すため、
非対称に倒してある。

### 3. 二値ではなく確信度を返す

「見つかった / 見つからない」しか表現できないと、`ひこうき雲 / 松任谷由実` のような
**曲名は確実に合っているがアーティストが違う**ケースを、存在しない曲と同列に扱うしかない。
`SongMatchService.FindCandidates` は確信度つきの候補列を返す。

| 状況 | 確信度 | reason |
|---|---|---|
| iTunes Track ID が一致 | 1.00 | `itunes_id` |
| 曲名・アーティストが逐字一致 | 1.00 | `exact` |
| 曲名キー一致 + アーティスト集合が一致 | 0.97 | `title_artist` |
| 曲名キー一致 + アーティストの主体が一致 | 0.95 | `title_primary` |
| 曲名キー一致 + アーティスト名が部分的に共通 | 0.90 | `title_overlap` |
| ── ここから上が自動採用（`AutoMatchScore` = 0.85）── | | |
| 曲名キー一致（その曲名は 1 件）+ アーティスト未記入 | 0.80 | `title_only` |
| 曲名が近く、アーティストも一致 | 0.65 | `fuzzy_title` |
| 曲名キー一致（その曲名は 1 件）+ アーティストが違う | 0.60 | `title_mismatch` |
| 曲名キー一致（複数該当）+ アーティスト未記入 | 0.55 | `title_ambiguous` |
| ── ここから上が要確認（`ReviewScore` = 0.50）── | | |
| 曲名キー一致（複数該当）+ アーティストが違う | 0.30 | `title_ambiguous` |
| 曲名が近いだけ | 0.35 | `fuzzy_title` |

`title_only`（0.80）を自動採用に上げていないのは意図的。誤って結びつけると歌唱が
別の曲にぶら下がったまま気づけないのに対し、新曲として登録してしまっても
統合候補に出るので後から畳める。

## 照合キーの保存（`song_match_keys`）

キーの計算は Go 側にある（SQL の immutable function より規則を書きやすく、テストしやすい）。
計算結果を `song_match_keys` に持ち、`name_key` の索引で引く。

```
ZIGG-ZAGG (feat. 初音ミク) / Junky
  → name_key="ziggzagg", artist_primary="junky", artist_tokens={junky}

私の彼はパイロット / ランカ・リー=中島愛
  → name_key="私の彼はパイロット", artist_primary="ランカリー",
    artist_tokens={ランカリー, 中島愛}
```

キーが腐らないようにする仕掛けが 3 つある。

1. `SongRepository` の `Create` / `Update` がキーも同時に書く（サービス層に任せない）
2. アーティストの改名・統合は同じトランザクションでキーを追随させる
3. `song_match_keys` は**計算元の曲名・アーティストを控えている**。起動時に `songs` と
   突き合わせ、ズレていれば作り直す

3 のおかげで「キー更新を呼び忘れた経路」があっても再起動で直る。
正規化ルールを変えたときは `songmatch.RulesVersion` を上げれば、
やはり起動時に全件が作り直される（マイグレーションを書く必要はない）。

## 照合が外れたときの受け皿（`song_merge_candidates`）

ルールをどれだけ良くしても、同一人物の別名義のように**文字列だけでは決められない組**は残る。
そこは新曲として登録するが、**黙っては作らない**。

`findOrCreateSong` は新曲を作る前に候補を引き、要確認（0.50〜0.85）の既存曲があれば
`song_merge_candidates` に記録する。曲の登録自体は止めない（配信の編集を人質に取らない）。

```
[INFO] 新規登録した楽曲が既存曲に似ています。統合候補として記録しました:
       "ひこうき雲" / "松任谷由実" ↔ "ひこうき雲" / "荒井由実" (score=0.60, title_mismatch)
```

記録された組はここに出る。解決は既存の統合機能（`POST /api/songs/{id}/merge`）。

- `/admin/merge-candidates` … レビュー用の一覧（`content:edit`）
- 楽曲詳細 … その曲に関係する候補をバナーで表示

「別の曲」で却下すると同じ組は二度と出ない。統合すると関係する候補は自動で閉じる。

### 既存データの走査（2 段構え）

取り込み時の検出は「これから作る曲」しか見ないので、**この仕組みを入れる前から
DB にあった重複には誰も気づけない**。`/admin/merge-candidates` の「既存データを走査」は
2 つの走査を続けて回す。

**① 曲名キーで束ねる**（`ScanDuplicates`）。`song_match_keys` を `name_key` で
グループ化し、複数該当する組を積む。確実で無料。本番 820 曲で 3 組。

**② 登録曲を丸ごと AI に見せる**（`ScanDuplicatesWithAI`）。①は
`GROUP BY name_key` なので、**キーが違う組は原理的に見つけられない**。

```
ホール・ニュー・ワールド / アラジンとジャスミン  → name_key = ホールニューワールド
A Whole New World      / アラジン            → name_key = awholenewworld
```

この 2 曲は同じ曲だが、どれだけ走査しても同じグループに入らないので
判定の AI にすら届かなかった。文字列側で寄せ方を工夫するより、一覧を丸ごと渡して
選ばせるほうが確実で単純。本番 819 曲で実測すると 3 組を検出し、いずれも①では
見つけられないものだった。

```
Idol / YOASOBI            ↔ アイドル / YOASOBI            英字表記と日本語表記の違い
スマイル・エンゲージ / Beit  ↔ スマイル・エンゲージ / Smile Engage  曲名とアーティスト表記の重複
ホール・ニュー・ワールド      ↔ A Whole New World            邦題と英題の同一曲
```

入力は大きい（819 曲で約 13k トークン）が出力は数組しかなく、入力は出力より一桁安い。
走査は滅多に回さないので割に合う。AI が落ちても①の結果は返す。

どちらも**統合は実行しない**。却下・統合済みの組は行が残るので蒸し返されない。

## 同名の組には 3 通りの正解がある

曲名キーがぶつかった組をどう扱うべきかは、**組ごとに違う**。本番データの 3 組がそのまま例になる。

| 組 | 同じ作曲か | 統合すべきか | 理由 |
|---|---|---|---|
| 惑星ループ（Eve / ナユタン星人） | ○ | **する** | `original_artist` が原唱と作曲のどちらを記録したかの違いでしかない |
| 翼をください（赤い鳥 / 桜高軽音部） | ○ | しない | 編曲が大きく違い、どちらを歌ったかが情報になる |
| オレンジ（SPYAIR / 逢坂大河ほか） | × | しない | 同名だが別の曲 |

ここで効いているのが `original_artist` が**単一の欄で 2 種類の関係を兼ねている**こと。
作曲者（ナユタン星人）と原唱（Eve）は別の関係で、どちらを入れても間違いではない。
つまり `惑星ループ / Eve` は誤データではなく、欄の意味が足りていないだけ。

そして 1 行目と 2 行目を分けているのは、metadata では表現できない
**「唱ったのがどちらの版かは、この DB にとって情報か」**という編集方針の判断になる。

だからこの分岐は自動化しない。AI には事実（同じ作曲か・編曲は同系統か）だけを答えさせ、
統合するかどうかは人が決める。統合は破壊的（統合元が消え、歌唱が移る）なので、
誤りのコストが「重複が残る」より明確に高い。

> 一度は「AI に『同じ曲か』と聞いて自動統合する」案を採ろうとしたが、実データで却下した。
> 翼をください に対して AI は正しく「同じ曲」と答えるが、その答えに従うと
> 分けておきたいものまで統合されてしまう。**正しい答えが有害になる**問いだった。

## 規則で決まらないものは AI が裁く（二段構え）

ここまでの規則をどれだけ磨いても、**文字列の比較では原理的に決まらない**組が残る。

- 同一人物の別名義（松任谷由実 = 荒井由実、ランカ・リー = 中島愛）
- 括弧内の未知語（`深昏睡` と `深昏睡 (Deep coma)` は同じ曲、
  `Starry night` と `Starry night (instrumental)` は別録音。どちらも語彙リストでは切れない）
- 曲名キーも trigram も一致しない同一曲（`Rumor` と `ルーマー`、
  `Plastic Love` と `プラスティック・ラブ`）

以前はこれを「学習層」（`song_aliases` / `artist_aliases`）に溜めて解いていた。
今は**読み込みのたびに AI が解く**。使い分けは候補の数で決まる。

### どちらを使うかは実測で決めた（2026-08-12、本番 255 行）

未照合の 297 行のうち、GT（人が保存した `performances`）が ±60 秒以内にある 255 行で、
本番と同じモデル・同じ判定規則・同じバッチ幅（8 行）で両方を走らせた。

| | 候補あり 212 行 | 候補ゼロ 43 行 | 合計 255 行 | input tokens |
|---|---|---|---|---|
| **候補を見せる** | 209（98.6%） | 0（構造的に不可能） | 209（82.0%） | 25k |
| **曲庫まるごと** | 211（99.5%） | 33（76.7%） | 244（95.7%） | 441k |

**誤答はどちらも 0。** 分からなければ null を返し、無理に近いものを選ばない。

読み取れることは 2 つ。

1. **候補があるうちは候補で足りる。** 曲庫を見せても +0.9% にしかならず、入力は 18 倍になる
2. **候補ゼロは召回の問題であって判断の問題ではない。** 候補の中に答えが無いのだから、
   どんなに賢い裁き手を置いても当たらない。曲庫でしか解けない例：

```
Rumor / Police Piccadilly     → ルーマー / ポリスピカデリー
Plastic Love / 竹内まりや     → プラスティック・ラブ
深昏睡 / 春野                 → 深昏睡 (Deep coma)
革命道中 / アイナ・ジ・エンド → 革命道中 - On The Way
キラキラ武士 / レキシ         → きらきら武士
```

なので二段にする。候補があれば候補だけ、無ければ曲庫を丸ごと。
これで 242/255（94.9%）を、全部を曲庫に回す場合の 1/4 のトークンで取れる。

### 判定の軸は「編曲が同じか」

この 1 本で、上の「3 通りの正解がある」で挙げた組が正しく捌ける。

| 組 | 判定 | 理由 |
|---|---|---|
| 惑星ループ（Eve / ナユタン星人） | 同一 | 歌唱者と原作者の違い |
| 翼をください（赤い鳥 / 桜高軽音部） | 別 | 編曲が異なるカバー |
| 深昏睡 / 深昏睡 (Deep coma) | 同一 | 副題の表記違い |
| Starry night / (instrumental) | 別 | インスト版 |
| ダーリン / ダーリンダンス | 別 | 別の楽曲 |

**カバーでも編曲が同じなら同一曲**にするのは seTORI のデータモデルの帰結。
誰が歌ったかは `performances` に記録するので、`songs` の行は原曲を指す。

### 同一人物かも同じ呼び出しで聞く

AI は曲を選ぶ時点で両方の歌手名を見ているので、分けて聞くのは往復が 1 回増えるだけ。
応答の `same_artist` は 3 値（true / false / 省略）で扱う。

- **true** … 別名義として申し送る（`artist_alias`）。編集フォームのチェックボックスに出し、
  **人が保存したときだけ** `artists.aliases` に入る
- **false** … 「別人」として `artist_alias_checks` に残す。次の読み込みで同じ提案を繰り返さない
- **連名は申し送らない**。`May'n & 中島愛` と `ランカ・リー=中島愛` では
  どの名前とどの名前が同じ人なのか定まらない。曲の照合自体は採用してよい

作曲者と原唱の取り違え（`メルト / 初音ミク` に対し DB は `ryo (supercell)`）は
「同じ曲だが別人」で、これが本番では珍しくない（`title_mismatch` 164 行のうち 96 種）。
ここを混同すると、その人の全楽曲に効く別名義が誤って作られる。

### バッチの行番号は、そのバッチの中でだけ意味を持つ

**実測で踏んだ罠。** 評価スクリプトで行番号を通し番号（0..254）にして、
応答の `k` をそのまま添字に使ったところ、モデルがバッチ内で 0 から振り直したときに
**別のバッチの答えを上書き**した。8 行すべて正解していた先頭バッチが丸ごと誤答として
記録され、精度が 95.7% → 89.8% に見えた。

厄介なのは、応答自体は正常な形をしていること。JSON も壊れず、件数も合い、
選ばれた曲も実在する。番号がずれていることを知る手立てが無い。

対策は 2 つだけ。

- 問いの行番号は**呼び出しごとに 0 から**振る
- 返ってきた番号がその呼び出しの行数を超えていたら**捨てる**（`applyVerdicts`）

バッチ幅も欲張らない（`aiMatchBatchSize = 8`）。実測で 8 行 0 誤答、10 行でも通るが、
失敗が無音である以上、稼げるトークンより検知できない誤りの方が高くつく。

### 曲庫はスナップショットで渡す

`CatalogForAI()` が `s1|曲名|アーティスト` の一覧を作る。短い id を振り直しているのは、
UUID を 820 行ぶん並べるとそれだけで入力の大半を占めるため。

一括処理では**開始時に一度だけ**作って使い回す。理由は 2 つ。

- 一覧は問いの先頭に置くので、内容が同じなら provider の prefix cache に載る
- その回の処理で自分が作った新曲を、次の行の照合相手にしない（AI の誤りが増幅する）

## 覚えておくのは 2 つだけ

学習層を廃止したので、照合の状態として残るのは次の 2 つになった。

### `artists.aliases`（同一人物の別名義）

その人の**全楽曲に効く**ので覚える価値がある。しかも文字列では原理的に解けない。

`artists.alias_of`（FK）にしないのは、曲が 1 つも無い名義は `artists` に行が無いため。
配列なら本体の行にぶら下げられる。照合時は各名前を本体へ寄せてから突き合わせる。

### `*_checks`（否定の記録だけ）

`artist_alias_checks` と `song_identity_checks` は **`same = false` だけ**を持つ。

肯定を残さないのは、残す先が既にあるから ── 楽曲の同一性は AI が読み込みのたびに解き、
結果は `performances` に残る。歌手の同一人物は `artists.aliases` に入る。

否定を残すのは、一括処理で確信度の高い AI 判定がそのまま `performances` になるため。
人が「これは違う」と消したものを、次の force 実行が同じ理由で書き戻してしまう。
「人が否決した組」を覚えておくのが、その唯一の歯止めになる。

### `song_aliases` は廃止した（migration 041）

表記 → 楽曲の対応表。AI が毎回解くので溜める必要が無い。節約も小さく、
未照合 82 行に対し表記の種類は 65（`革命道中` が 7 回など）で、
同じ表記を二度聞く率は 1.26 倍にすぎない。

代わりに消えたものが 2 つある。どちらも「AI が毎回解く」で置き換わっている。

- 統合からの学習（`merge`）… 統合はもう別表記を作らない。付け替えるのは否定の記録だけ
- コメントタブの候補確定（`POST /api/streams/{id}/comment-songs/match`）…
  照合を決めるのは編集フォームへ読み込むときの仕事になった

## AI による重複判定（助言のみ）

レビュー画面の「AI に判定させる」で、未判定の候補についてまとめて 1 回問い合わせる。

聞くのは事実だけ：

- `same_composition` … 元をたどれば同じ曲か
- `same_arrangement` … 編曲が同系統か
- `role_a` / `role_b` … それぞれの立ち位置（「原曲（1971年・フォーク）」など）
- `recommendation` … 上 2 つから機械的に決まる（両方 true のときだけ `merge`）

**統合は実行しない。**候補を並べ替えて、判断材料を添えるだけ。

実測（本番 DB の 3 組、gpt-5.6-luna）:

```
オレンジ     作曲別・編曲別 → keep_separate  「同名だが別作品の別楽曲」
翼をください  作曲同・編曲別 → keep_separate  「同じ曲だが原曲とバンド編成が異なる」
惑星ループ    作曲同・編曲同 → merge          「Eve版はナユタン星人の原曲を歌唱したカバー」
```

3 組とも意図どおり。ただし 惑星ループ の説明で AI は Eve を「カバー」と書いており、
これは事実として争いがある。**推奨（merge）は正しいが理由は疑わしい**という状態で、
だからこそ理由を UI に出している。冷門曲では AI が作話するので、
説明が不自然かどうかが唯一の防御線になる。

判断材料として iTunes の収録アルバム・再生時間・試聴も候補画面に出す。
「編曲がどれだけ違うか」は曲名とアーティストからは分からない。

## 残っているもの

### `song_artists` に role を持たせる案（検討済み・見送り）

`original_artist` が作曲者と原唱を単一の欄で兼ねているのが、惑星ループ 型の
重複が生まれる根本原因。`song_artists` は既に多対多なので、`role`
（composer / vocalist / feat）を持たせれば 1 曲に両方を記録でき、
どちらの表記で来ても同じ曲に当たる。重複が発生しなくなる。

**2026-08-08 時点では見送った。** 理由は収益とコストが釣り合わないこと。

- 全庫走査で見つかった 惑星ループ 型の重複は **1 組**だけ
- 既存の統合 + AI の照合でほぼ同じ結果になる。統合すると
  「惑星ループ / Eve」が別表記として学習され、以後どちらの表記でも当たる。
  差は「人が一度ボタンを押すかどうか」しかない
- 一方コストは大きい。820 曲の `original_artist` は 1 つの文字列しか無く、
  それが作曲なのか原唱なのか機械的には判定できない。さらに `artists` には
  `"GEMN, 中島健人 & キタニタツヤ"` のような連名がそのまま 1 アーティストとして
  39 件入っており、role を意味あるものにするには連名の分割が先に要る。
  分割は読み仮名の管理・アーティストページ・集計まで波及する

**やるとしたら別の動機で。** 「作曲者で曲を辿る」「初音ミクが歌った曲」
「P 主ランキング」のような機能を作るときには role と連名分割が本来必要になる。
そのときは重複解消は副産物として付いてくる。重複対策を動機に始めるのは割に合わない。

なお role を入れても 翼をください 型（編曲違いで意図的に分ける）は解けない。
あれは artist 欄の語意の問題ではなく編集方針の問題で、別の話。
- 別名義の種は AI と手動のみ。MusicBrainz には正式な alias / performance name の
  関係データがあるので、取り込めば初期状態から効かせられる。

## 実測した照合精度（2026-08-09、本番データ）

**人手で確認済みの `performances` を正解として突き合わせた結果。**

| | 件数 | |
|---|---:|---|
| 突き合わせた組 | 4162 | |
| 照合が**誤り** | **6** | 0.14% |
| 照合が正しい | 3952 | |
| 照合しなかった | 204 | 4.9% |

**出した答えの正解率は 99.85%。** 保守的な設計（自動採用は 0.85 以上、
それ未満は人へ回す）は意図どおり効いていて、**改善の余地は「誤りを減らす」側には
ほとんど無く、「照合しなかった 204 件」の側にある**。

### 測り方と、その限界

評価集合は `is_processed` かつ performances と comment_songs の両方を持つ配信。
抽出側と正解側を**開始時刻の近接（±20 秒）**で対応付け、その組で曲 ID を比べる。

限界を承知で使うこと：

- **時刻だけで対応付けている。** 曲名を間違えていても、正しい曲の ±20 秒に
  落ちていれば「対応した」と数えられる
- 開始時刻は抽出側も正解側も**同じコメントの時刻表記に由来する**ので、
  時刻が一致すること自体は精度をほとんど語らない（89.4% が 0 秒一致）
- 対応付けは厳密な 1 対 1 ではない。メドレーや密な連唱で甘くなる

したがってこの数字は **「照合が正しい曲を選べたか」の指標**であって、
「抽出が正しかったか」の指標ではない。抽出側の評価は `cmd/setoribench`。

### 未照合を機構ごとに数え直した（2026-08-11）

同じ 4162 組について、「照合できないなら**何があれば照合できるか**」を
実際に変換を当てて確かめた（`gt_report.csv` / `gt_unmatched.csv`。再生成できるので
リポジトリには置いていない）。未照合は 213 件。

| 解決機構 | 件数 |
|---|---:|
| **AI 正規化が壊している（抽出のままなら一致）** | **78** |
| 全く別の歌手名。AI か人の判断が要る | 43 |
| 連名 / CV クレジットの書き方 | 19 |
| 片方が他方の部分文字列 | 17 |
| 曲名が全く違う（誤字・日英別名） | 15 |
| 副題（区切り以降）を落とすと一致 | 13 |
| `feat.` の有無 | 10 |
| その他 | 18 |

最大の 78 件は照合側ではなく**正規化側の問題**だった（上の「`a` は書き換えさせない」）。
`resolveOne` は照合が外れたら抽出のままで引き直すので、既存データもこれで救われる。

さらに「実際に AI へ送られる候補」を本番の 819 曲に対して計算すると：

- 185 件は候補が出る。**うち 98% は正解が候補に含まれている**
- 28 件は候補ゼロ。誤字（`創生`/`創聖`）・日英別名（`Rumor`/`ルーマー`）が中心で、
  規則でも trigram でも届かない

その 28 件に**カタログ 819 曲を丸ごと渡して AI に選ばせると 25 件正解・誤答 0**
（1 回の呼び出し、13k トークン）。RAG は要らない ── この規模なら全件が prompt に入る。
検索層が必要になるのは曲庫が数万件になってから。

### 照合しなかった 204 件の内訳

大半は照合アルゴリズムのせいではなく、**空の正規化名で照合していた不具合**
だった（`a0973fb` で修正）。残りの内訳は、その分を除いてから数え直すこと（TODO 38）。

観測された、正規化で拾えていない型：

- **Unicode の変体** … `~`(U+007E) と `〜`(U+301C)、`'` と `’`、`é`、連続空白
- **アーティストの表記ゆれ** … `315 STARS`/`315 ALLSTARS`、`Team halcyon`/`halcyon`、
  `稀羽すう feat.獅子神レオナ`/`稀羽すう`。曲名が一意なら歌手側で否決しないこと
- **別名** … `Hello, SEKAI`/`ハローセカイ`、`Rumor`/`ルーマー`（曲庫まるごとの AI 判定で解ける組）
- **誤字** … `Famme Fatale`/`Femme Fatale`、`Trio Dream`/`Trio Dreams`

## 照合は保存しない

`comment_songs` / `holodex_songs` に保存するのは **抽出・正規化・拍手 end まで**。
照合（どの楽曲か）は配信詳細を読むたびに計算する（`ResolveForDisplay`）。

分けるのは、2 つの半分でコストと寿命がまるで違うから：

| | 抽出・正規化・拍手 end | 照合 |
|---|---|---|
| コスト | AI・yt-dlp。15 秒〜数分、課金あり | 索引を引くだけ。数ミリ秒 |
| 依存先 | `comment_raw`（変わらない） | `songs`（毎日変わる） |
| 古くなるか | ならない | **常になる** |

保存していた頃は、古くなる側を追いかけるために `backfill-matches` という端点、
`comment_songs_hash` を壊さないための注意書き、「候補が変わったか」の差分判定が要り、
しかもコメント経路と Holodex 経路で保存する / しないの判断が食い違っていた。
読み取り時に計算すればどれも要らない。

## 継続して測る（`cmd/setoribench -match`）

上の一度きりの調査を、回せるベンチにしたもの（2026-08-10）。

```
go run ./cmd/setoribench -mode stored -nofilter -baddump /tmp/bad.json
go run ./cmd/setoribench -mode stored -nofilter -noalias   # 別名義（artists.aliases）を外した場合との差
```

**抽出が当てた曲（TP）だけを照合の評価対象にする。** 抽出を外した曲まで混ぜると、
照合の成績が抽出の成績に汚染されて、どちらを直したのか分からなくなる。

**主指標は「DB の表記と抽出の表記が逐字で食い違う組」に絞る。** 正解の楽曲の一部は
そのコメント自身から `findOrCreateSong` で作られていて DB 表記＝コメント表記に
なっているため、混ぜたまま測ると照合が何もしなくても 0.92 が出る（実測）。

指標を 4 つに割るのは**間違え方でコストが違う**から。まとめて「精度」にすると、
閾値を下げて誤採用を増やす改悪が数字の上では改善に見える。

| 指標 | 意味 | コスト |
|---|---|---|
| auto_match_rate | 0.85 以上で自動採用できた | — |
| **false_match_rate** | 自動採用したが**別の曲**だった | **最重い**。誰も気づかない |
| review_rate | 0.50〜0.85 で人手に回った | 運用コスト。誤りは残らない |
| no_candidate_rate | 候補すら出ず新規登録される | 統合候補に出るので回復可能 |

### 手元 726 本・GT 4230 曲での基準値（2026-08-10）

| | 主指標（803 件） | 参考（全 4123 件） |
|---|---:|---:|
| auto_match_rate | 0.593 | 0.921 |
| false_match_rate | 0.005（4件） | 0.001 |
| review_rate | 0.284（228件） | 0.055 |
| no_candidate_rate | 0.123（99件） | 0.024 |

読み取れたこと：

- **誤採用 4 件はすべて DB 側の重複が原因**で、照合規則の誤りではない。
  `弱虫モンブラン` と `弱虫モンブラン (Reloaded)`、`惑星ループ`（ナユタン星人 / Eve）、
  `スマイル・エンゲージ` の 3 重登録。統合候補を片付ければ 0 になる
- **人手に回った 228 件は最有力候補が 228/228 で正解。** 0.50〜0.85 の候補を
  人に見せる設計（`title_only` / `title_mismatch`）は機能している。
  ただし正解データは人がこのパイプラインの提案を承認して作った面があるので、
  「過去の判断と一致した」に近い数字であることは割り引く
- 候補が出なかった 99 件は 71 件が曲名の誤字・表記ゆれ、
  28 件は `name` に `曲名/アーティスト` が入ったままの**抽出の失敗**

`-noalias` は手元では差が出ない（`artists.aliases` を持つ行が無いため）。
**上の数字は学習ゼロの下限**で、確定操作が貯まってから測り直すと学習層の寄与が出る。
