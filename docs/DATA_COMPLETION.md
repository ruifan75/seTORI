# データ補完と検証：終了時間の由来をどう扱うか

歌唱記録のうち **終了時間だけは、ほとんどが推定値**である。
開始時間はコメントに書かれているが、終了時間を書く投稿者は少ない。

このドキュメントは「その推定をどこまで信じるか」「誰がいつ確定させるか」を扱う。
解析そのもの（コメントから曲を取り出す部分）は [`AI_PIPELINE.md`](./AI_PIPELINE.md) を参照。

---

## 1. 終了時間はどこから来るのか

現在 5 つの供給源がある。**この順で確度が下がる。**

| 由来 | 仕組み | 確度 |
|---|---|---|
| 人手 | 編集画面で入力・保存 | 確定 |
| Holodex | Holodex のセットリストが持っている | 確定扱い |
| コメント明示 | `0:12:08 ; 0:16:13 花に亡霊` のように投稿者が書いている | 確定扱い |
| **chat 拍手検出** | live chat の「純粋な拍手」の塊から逆算（`pkg/chatend`） | **MAE 2.18 秒 / 99% が ±10 秒以内**（1,445 曲で実証） |
| iTunes 再生時間 | 紐付いた iTunes トラックの長さを開始時間に加算 | 弱い（音源とパフォーマンスの長さは違う） |
| 次の曲の開始時間 | 次の曲が始まるまでを 1 曲とみなす | 弱い（MC や雑談が挟まる） |
| チャプターの区切り | 配信者が付けた目次の次の章節の開始 | 弱い（＝上と同じもの。`end_source` も `next_start` にする） |
| 既定値 240 秒 | 何も手がかりが無いとき | ほぼ当てずっぽう |

推定側の優先順位は `EndTimeEstimateService` にあり、
iTunes → 次の曲の開始 → 既定 240 秒（`DefaultSongDuration`）の順。

### 実測の内訳（2026-08-07、`comment_songs` 10,109 件）

| 由来 | 件数 |
|---|---:|
| chat 拍手検出 | 3,500 |
| コメントに明示 | 3,470 |
| **終了時間なし**（＝表示時に推定へ回る） | **2,863** |
| コメント明示 + chat も検出（照合用） | 276 |

**拍手検出は既に最大の供給源であり、コメント明示より多い。**
弱いのは 2,863 件の「終了時間なし」層で、ここが iTunes 逆算や 240 秒既定に頼っている。
**視聴者に検証を頼むならこの層から**、というのが優先順位の根拠。

### 拍手検出はいつ走るのか

コメント解析の第 6 ステップで、**全曲に対して無条件に走る**。
「終了時間が無いものだけ」ではない。

```go
endByStart := s.DetectEnds(videoID, durationSeconds, starts)  // 全曲に対して検出
for i := range songs {
    if hasExplicitEnd {
        songs[i].ChatEnd = chatEnd            // 採用せず、照合値として記録
        songs[i].EndDiff = abs(end - chatEnd)
    } else {
        songs[i].End = chatEnd                // ここで初めて採用
    }
}
```

検出は無条件、**採用が条件付き**。既に明示の終了時間がある曲でも検出結果を
`ChatEnd` / `EndDiff` に残し、編集画面で「Chat との差 N 秒」の警告と
「Chat の値を適用」ボタンとして出している（差が 10 秒以上のとき）。
つまり拍手検出は**穴埋めであると同時に、コメント値の監査役**でもある。

> ⚠️ live chat は `yt-dlp` で丸ごとダウンロードする（`fetchLiveChat`、タイムアウト 3 分、
> `videoID.live_chat.json` としてファイルキャッシュ）。歌枠の live chat は数十 MB に
> なることがあり、**大量の配信を一括処理するときは AI 解析より重くなりうる**。

#### この実行に `--print` を足すときは `--no-simulate` が要る

同じ呼び出しに相乗りして再生可否（`availability` / `playable_in_embed`）を拾っている
（issue #3。追加のリクエストは発生しない）。そのとき **`--print` は `--simulate` を含む**
ことに注意する ── ファイルを書く実行にそのまま足すと、yt-dlp は
**何も書かずに終わる**。

実測：`--print` を足しただけで `live_chat.json` が作られなくなった。
落ちも警告も出ず、症状は「この配信に live chat replay がありません」だけなので、
**原因に辿り着けない**。ファイルを書く実行には必ず `--no-simulate` を添えること
（`availabilityArgs(true)`。チャプター取得は `--print` しかしないので不要）。

拾った値の扱い（`--ignore-no-formats-error` の下では削除済みの動画でも
`availability = public` が返ること、会限が `subscriber_only` かつ
`playable_in_embed = true` を返すこと）は `docs/STREAM_VISIBILITY.md`。

#### 取得に失敗するとき

`[chatend] ... live chat を利用できません` のログは原因を名指しする。よくあるのは 3 つ：

| ログ | 原因 | 対処 |
|------|------|------|
| `yt-dlp が実行できません` | 未インストール | 本番イメージには同梱済み（`backend/Dockerfile`）。手元なら `brew install yt-dlp` |
| `YouTube に BOT 判定されました` | IP 単位で弾かれている | 管理→設定の「YouTube cookie」に cookies.txt を貼る |
| `この配信に live chat replay がありません` | 本当にチャットが無い配信 | 対処不要 |

cookie は DB 上で暗号化して保存され、再起動なしで反映される。ファイルで渡したい場合は
`YTDLP_COOKIES_FILE` に置き場所を書く（起動時に一度だけ読む）。

> 新しい yt-dlp は YouTube の署名解決に JS ランタイム（deno）を要求する。本番の alpine
> イメージには無いので、映像フォーマットは 1 つも取れない。字幕だけが欲しいので
> `--ignore-no-formats-error` を渡して先へ進めている。**deno を入れる必要は無い**
> （live chat は innertube のチャット API 経由で、署名を通らない）。
> このフラグが無いと、字幕を選び終えた直後に「Requested format is not available」で落ちる。

#### あとから end だけ埋める

一括プレ分析は comment_raw の hash キャッシュに命中すると拍手検出まで飛ばすので、
「AI 分析は済んでいるが end が無い」配信が残る。埋め直しは AI を呼ばない専用の経路を使う：

- 編集画面のコメントタブの拍手アイコン（1配信）
- `POST /api/chat-ends/backfill?concurrency=3`（comment_songs を持つ全配信）

### `is_end_time_estimated` の意味に注意

このフラグは「推定かどうか」ではなく **「信頼できる終了時間が無い」** を表す。

拍手検出で埋めた場合は `IsEndTimeEstimated = false`（＝推定扱いにしない）。
精度が MAE 2.18 秒あり、iTunes 逆算などとは信頼度が違うため。
拍手由来であることは `ChatEnd` に値が入っていることで判別する。

実測でも、フラグが立っているのは「終了時間なし」の 2,863 件だけで、
他の由来はすべて `false` になっている。

## 2. 現状の欠落：`performances` に由来が残らない

```
performances
  start_seconds | integer  not null
  end_seconds   | integer  not null   ← 数値のみ
```

**保存された時点で由来の情報は失われる。**
人が入力したのか、Holodex 由来か、拍手検出か、240 秒の既定値かを、後から区別できない。

> ここから下は **2026-08-11 に `end_source` / `end_confirmed` を入れるまでの話**。
> 現在は保存時に由来を送っている（本番の既存 4,267 件は `unknown` のまま残る）。
> 判断の経緯として残す。

当時はこれで回っていた。「編集画面で保存された ＝ 人が確認した」という暗黙の規則が
成立していたからで、実際に既存の 4,268 件はすべて人手を通っている。

### なぜこれが問題になるのか

**配信を一括処理して performance を自動作成すると、この規則が黙って崩れる。**

自動生成された行と人手確認済みの行が見分けられなくなり、しかも**事後に遡って
区別することができない**（`created_at` で推測するくらいしか手が無い）。
エラーも警告も出ないまま、「確認済み」という情報だけが失われる。

このプロジェクトが繰り返し踏んできた「失敗が成功に見える」型の問題と同じ構図で、
違うのはバグではなく設計上の欠落だという点だけ。

## 3. 提案：由来と確認状態を**分けて**持たせる

`performances` に 2 列を足す（migration が要る）。

```
end_source    : 値がどこから来たか
end_confirmed : 人が見て認めたか（boolean）
```

### なぜ 1 列では足りないのか

当初は「人が確認したら `manual` に変える」という 1 列案だった。しかしこの場面が扱えない：

> AI が推定した終了時間を利用者が見て、**正しいと判断してそのまま保存した。**

このとき値の出どころは依然として `chat` だが、人の確認は済んでいる。
1 列だと「`chat` のまま」＝未確認に見えるか、「`manual` に変える」＝どう推定されたかを失うかの
どちらかになる。**由来と確認は直交する属性**なので列を分ける。

区別できないと実際に困るのは検証 UI が訊く相手を選ぶとき。
「chat 由来だが確認済み」と「chat 由来で誰も見ていない」を分けられないと、
確認済みの曲まで利用者に訊いてしまい、消耗させる。

### `end_source` の値

| 値 | 由来 | 確度 |
|---|---|---|
| `manual` | 人が編集画面で値を入力・変更した | 確定 |
| `holodex` | Holodex 提供 | 高い |
| `comment` | コメントに明示されていた | 高い |
| `chat` | 拍手検出 | 高い（MAE 2.18 秒） |
| `itunes` | iTunes の再生時間から逆算 | 低い |
| `next_start` | 次の曲の開始時間 | 低い |
| `default` | 240 秒の既定値 | ほぼ無い |
| `unknown` | 由来を記録する前に作られた行 | — |

> フロントエンド（`StreamDetailPage`）は既に `endSource` を
> `'comment' | 'chat' | 'holodex' | 'itunes' | 'manual'` として編集中ずっと追跡している。
> **保存時に API へ送っていないだけ**で、値そのものは既に手元にある。

### 既存データの扱い

既存の 4,268 件は `end_source = 'unknown'` / `end_confirmed = true` とする。

すべて人手の編集画面を通っているので確認済みなのは確かだが、**由来までは遡れない**ため
`manual` と断定はしない。`unknown` にしておけば「記録を始める前のデータ」だと後から分かる。

### これが入ると導けること

- 一括自動作成が `end_confirmed = false` で書ける（人手確認を詐称しない）
- 検証 UI が訊く相手を選べる
  （`end_confirmed = false` かつ `end_source` が `itunes` / `next_start` / `default`）
- 自動反映の閾値を状態ごとに変えられる
  （未確認の `default` を上書きするなら 1 票、確認済みを覆すならもっと多く）

## 4. コミュニティ検証：仕組みは既にある

「再生中に視聴者へ正しさを訊く」ために必要な部品は実装済み。
**足りないのは「どれが未検証か」を示すことだけ。**

| 部品 | 実体 | 役割 |
|---|---|---|
| 再生バーの旗アイコン | `PlaybackFeedback.tsx` | 押した瞬間の再生位置を開始/終了として送る |
| 提案の受け皿 | `edit_suggestions` テーブル | 匿名でも投稿でき、レビューを経て反映 |
| 自動反映 | `tryAutoApply` / `AutoApplySettings` | 条件を満たせば人手を介さず反映 |

自動反映の既定条件（`DefaultAutoApplySettings`）：

```
Enabled = true / MinVotes = 2 / MaxSpreadSeconds = 3 / MaxDeltaSeconds = 5
```

**異なるログインユーザーが 2 人以上、ばらつき 3 秒以内**で近い値を出していれば中央値を反映する。
匿名は票に数えない。対象が提案後に編集されていれば自動反映せず人手に回す。
条件は管理画面（レビュー画面の「自動反映の条件」）から変更できる。

## 5. 進める順序

```
27. end_source を持たせる  →  28. 一括で performance を自動作成  →  29. 再生中の検証 UI
   ✓ 2026-08-11              ✓ 2026-08-13（本番未実行）            未着手
```

**27 を 28 より先にやること。** 逆にすると自動生成されたデータが既存データに
混ざり込み、区別する手段が永久に失われる。この順で入れたので、一括が作った行は
`end_source`（確度）と `created_via` / `batch_run_id`（誰が作ったか）で区別できる
── 一括は `end_confirmed = false` で書き、実行単位で撤回もできる（`docs/SETLIST_FLOW.md`）。

各項目の詳細な作業内容は `TODO.md` の 27〜29 を参照。

### 設計上の判断として残しておくこと

- **拍手検出は既に十分な精度**（MAE 2.18 秒）。ここを疑うより、
  iTunes 逆算と 240 秒既定に頼っている 2,863 件を潰す方が費用対効果が高い
- 検証を訊く相手を絞ることが重要。全部訊くと利用者が消耗し、誰も答えなくなる
- 拍手検出は穴埋めだけでなく**監査役**でもある。コメントに明示があっても検出は走らせ、
  差が大きければ警告を出す設計は維持する
