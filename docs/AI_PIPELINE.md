# AI 解析パイプライン：入出力フォーマット

コメントから歌唱記録を起こすとき、AI を呼ぶのは **1 回**（統合経路）。
抽出・正規化・重複排除をまとめて 1 度の呼び出しで行う。
チャットの拍手から曲の終了時間を検出する処理（`pkg/chatend`）は純粋な文字列ロジックで、AI は使わない。
終了時間の由来と確度の扱いは [`DATA_COMPLETION.md`](./DATA_COMPLETION.md) を参照。

```
comment_raw（生コメント。複数の視聴者が投稿していることが多い）
   │
   │  ① 前フィルタ：タイムスタンプを含む行だけ残す（Go・正規表現）
   ▼
   │  ② AI 呼び出し：抽出＋正規化＋重複排除
   │     AI は「どの行が曲か」「どの行同士が同じ曲か」を指し示すだけ
   ▼
   │  ③ Go の確定的な組み立て：時刻計算・逐語チェック・行の統合
   ▼
   │  ④ フィルタ / 重複排除 / 妥当性検証（安全網）
   ▼
   │  ⑤ comment_songs へ保存（**照合結果は落として**保存する）
   │     └ DB 照合は保存の対象外。stripMatchForStorage が剥がす
```

⑤ の照合そのものは AI を使わない（規則ベース。[`SONG_MATCHING.md`](./SONG_MATCHING.md)）。
ただし照合が決着しなかったときに限り、追加で AI を呼ぶ経路が 2 つある。
どちらも**事実の判定だけをさせ、データの書き換えは人か規則が行う**。

| いつ | 何を聞くか | 結果の扱い |
|---|---|---|
| 入力元を編集フォームへ読み込むとき（自動） | 「この表記はどの登録曲か」「歌手は同一人物か」 | 曲はその場で採用する。歌手の別名義は**申し送るだけ**で、登録は人が保存したときだけ |
| 重複候補のレビュー（手動） | 「この 2 曲は同じ作曲か・編曲は同系統か」 | **助言として表示するだけ。統合は人が実行する** |

否定（「別の曲」「別人」）は永続化して二度聞かない。肯定は保存しない
── 曲は毎回解き直しても数え切れるほど安く、歌手は `artists.aliases` に残るため。
詳しくは `docs/SONG_MATCHING.md` の「覚えておくのは 2 つだけ」。

## 経路は 3 段階で退避する

```
統合（grouped）─ 失敗 →  2 段階（抽出→正規化）─ 失敗 →  純正規表現
```

統合経路が既定（2026-08-07 から）。ベンチマークで誤検出が 0 になり、費用も最も安かった。

2 段階は退避先として残しているほか、**元コメントが存在しない経路では今も現役**：
Holodex 由来の曲と、編集画面の手動「AI 正規化」ボタンは `BatchAINormalization` を直接呼ぶ。
そちらには突き合わせるコメント行が無いため、統合経路は使えない。

## 実例の採取方法

このドキュメントの入出力例は、すべて**実際の稼働ログから採取したもの**
（2026-08-07、配信 `hVfDBfreYNI`、モデル `gpt-5.6-luna`）。再取得するには
`PUT /api/logs/level {"level":"DEBUG"}` にしてから
`POST /api/streams/{id}/comments/analyze?force=true` を叩き、ログの
`AI grouped input` / `AI grouped raw response` を見る。

## ① 前フィルタ（AI 呼び出し前）

`extractTimestampLinesGrouped()` がタイムスタンプらしき文字列を含む行だけを残す。
**これがトークン量を決める最大の要因**で、生コメント全体を送ることはない。
統合経路ではどのコメント由来かも保持する（AI に「別の人が投稿した同じセトリ」を認識させるため）。

実測（コメントを持つ 845 配信）：

| | 中央値 | 平均 | p90 | 最大 |
|---|---:|---:|---:|---:|
| 残る行数 | 14 行 | 18 行 | 43 行 | 99 行 |
| 送信文字数 | 390 字 | 528 字 | 1,364 字 | 3,694 字 |

### 重複は前処理では落としていない

1 つの配信に複数の視聴者がセトリを投稿することがあり、**その場合は全員ぶんの行がまとめて
AI に渡る**。前処理に重複排除は無い。

実測：セトリを含むコメントが 2 件以上ある配信は **59.3%**、AI に送っている行の
**26.1% が重複**（複数コメントがある配信に限れば 32.4%）。

ただし**重複をそのまま落とすと情報を失う**。片方にアーティスト名、もう片方に終了時刻、
という形で補完し合っているため。

- 正規化して**完全一致**する行 … 4.2%。落としても無損
- 表記が異なる重複 … 21.9%。落とすと補完が効かなくなる

統合経路はこの補完関係を AI に判断させ、実際の統合は Go 側が行う（後述）。

---

## ② AI 呼び出し：抽出＋正規化＋重複排除

`pkg/comment/ai_grouped.go` の `ParseNormalizeAndDedupWithAI()`。

### 設計の要点：AI に値を合成させない

AI が担うのは**指し示すこと**だけ：

- どの行が歌唱か
- **どの行同士が同じ曲か**（`src` に行番号を列挙させる）
- 原文のどこが時刻・曲名・アーティストか

秒数への変換、複数行の統合、妥当性検証はすべて Go 側が確定的に行う。
AI が返した曲名・アーティストは、**`src` に挙がった行のいずれかに逐語で存在する場合のみ**
採用される（`isVerbatim`）。幻覚が数値や名称へ混ざる余地を構造的に潰している。

正規化フィールドだけは例外で、逐語チェックにかけない（意図的に原文と変える作業のため）。
そのため原文フィールドと正規化フィールドを**別のキー**で返させている。

### 入力

- system prompt：固定 2,166 字（`groupedAISystemPrompt`）
- user message：コメントの区切りを見せたまま通し番号を振った候補行

```
以下は同じ配信に投稿された 1 件のコメントから抽出した 10 行です。同じ曲を指す行はまとめ、
まとめた行番号を src に列挙してください。歌唱行のみを返してください。

--- コメント 1 ---
1) 9:26 『さよなら、花泥棒さん』
2) 20:42 『群青』
3) 32:30 『秒針を噛む』
4) 45:43 『Climax Jump』
5) 1:01:21 『君の知らない物語』
6) 1:15:19 『Part of your world』（英）
7) 1:23:12 『独りんぼエンヴィー』
8) 1:30:48 『夜明けと蛍』
9) 1:46:35 『愛・おぼえていますか』（アカペラ）
10) 2:02:43 『透明人間』
```

### 出力

**歌唱行だけ**を返させる（非歌唱行は要素を作らない）。抜粋：

```json
[
  {"src":[1],"ts":"9:26","te":"","nv":"さよなら、花泥棒さん","av":"",
   "n":"さよなら、花泥棒さん","nr":"さよならはなどろぼうさん","a":"","ar":"","t":[],"c":0.98},
  {"src":[9],"ts":"1:46:35","te":"","nv":"愛・おぼえていますか","av":"",
   "n":"愛・おぼえていますか","nr":"あいおぼえていますか","a":"","ar":"","t":["acappella"],"c":0.98}
]
```

| キー | 意味 |
|---|---|
| `src` | まとめた元の行番号（1 始まり）。1 行だけなら要素 1 つ |
| `ts` / `te` | **原文に書かれている時刻文字列をそのままコピー**。秒への変換は Go 側 |
| `nv` / `av` | 曲名・アーティスト（原文のまま）。`src` のいずれかの行に逐語で現れる必要がある |
| `n` / `a` | 正規化後の曲名・アーティスト。**`a` は行に書かれていればそのまま**（下記） |
| `nr` / `ar` | 平仮名の読み |
| `t` | バージョンタグ。下記 7 種のみ |
| `c` | 確信度 0.0–1.0 |

タグは 7 種に固定：`acoustic` / `piano` / `弾き語り` / `acappella` / `short` / `full` / `medley`
Go 側で語彙外の値は落とす（`filterAllowedTags`）。誤ったタグを作るより付かない方が害が小さい。
ただし**同じ意味の別の言い方は正規のタグへ寄せる**（`tagSynonyms`）。`1chorus` を
黙って捨てていた頃は、正規化後の曲名からその語が既に消えているため情報が復元できなかった。
原文の曲名に `1chorus` 等があれば `short` を補う（`normalizeTags`）。

### `a`（アーティスト）は書き換えさせない

本番の GT 4162 組で数えると、ここの扱いで照合率がはっきり割れていた。

| | 件数 | 照合できた |
|---|---:|---:|
| 行に歌手あり → AI がそのまま | 3799 | **96.8%** |
| 行に歌手あり → AI が別名に変えた | 311 | **74.0%** |
| 行に歌手なし → AI が補った | 49 | 85.7%（下記のとおり無意味） |

原因は `a` を「原曲のアーティスト名」と定義していたこと。DB の `original_artist` は
**カバーした歌手**を持っていることが多いので、原曲へ「訂正」すると DB から離れる。

```
涙そうそう / 夏川りみ      → BEGIN             （DB は 夏川りみ）
私は最強 / Ado            → Mrs. GREEN APPLE  （DB は Ado）
翼をください / 桜高軽音部   → 赤い鳥            （DB は 桜高軽音部）
```

最後の組は `SONG_MATCHING.md` が「編曲が違うので分けたまま」と書いている当のもの。

### 書かれていない歌手は**補わない**

上の 85.7% は「補った結果 GT に当たったか」であって、「補わなければ当たらなかったか」ではない。
数え直すと、**歌手が書かれていなかった 49 行はすべて、その曲名が DB 内で唯一だった**。

| | 件数 |
|---|---:|
| その曲名は DB で唯一（歌手なしでも `title_only` で候補に出る） | **49** |
| その曲名は DB に複数（歌手で選ぶしかない） | **0** |

つまり補って得たのは確認を省けたこと（42 行）だけで、代わりに 7 行で誤った歌手が入り、
0.95 の自動採用として**人の確認を通らずに保存**された。誤りはマイナーな曲に集中していて、
Re:AcT のオリジナル曲（`はっぴーでいず！`『アイリス』`Mornin' Bell`）に、同名の有名曲の歌手を当てていた。

一般化すると、曲名 A に DB 内で n 曲あるとき推測が当たる確率は 1/n で、
n=1 なら**そもそも補う必要が無い**。どちらの場合も補う理由が無い。

空のままなら `title_only` 0.80 に落ちて人の確認に回る。確認が要ることが可視化されるので、
「DB には A2 しか無いが実際に歌われたのは A1」のような取り違えもその場で直せる。
対象は全体の 1.2%（49/4162）なので、増える手間は小さい。

> キー名が 1〜2 文字なのは意図的。キーは要素ごとに繰り返され出力トークンを大きく食う。
> 長いキー（`normalized_name_reading` 等）にすると出力が約 1.9 倍になり、
> 出力単価は入力の 6 倍なので費用に直結する。Go のフィールド名は長いまま保っている。

### 統合の判断基準（プロンプトで指示している内容）

- 開始時刻がほぼ同じで同じ曲を指していれば、表記が違ってもまとめる
- **同じ曲名でも開始時刻が大きく離れていれば別の歌唱**（1 配信で 2 回歌うことがある）
- メドレーで連続する曲はそれぞれ別扱い

## ③ Go の確定的な組み立て

`buildSongsFromGrouped()`。`src` に挙がった行を 1 つずつ `ParseComment()` にかけ、
`mergeParsedSong` で畳み込んでから、AI の指摘を条件付きで重ねる。

1. `src` の行番号を検証（範囲外・重複は捨てる）。有効な行が 0 なら要素ごと捨てる
2. 各行を確定的にパースし `mergeParsedSong` で統合（各フィールドの最も情報量の多い版を採る）
3. `ts` / `te` を `parseTimestampString()` で秒に変換して上書き
4. `nv` / `av` は `src` 全体に対する逐語チェックを通った場合のみ上書き
   （統合の結果、歌手名が別の行から来ることがあるため）
5. 正規化フィールドを載せる。空なら原文側にフォールバック
6. タグを既知の 7 語彙へ丸める

## ④ 安全網（フィルタ / 重複排除 / 検証）

統合経路でも `FilterSongs` → `DeduplicateSongs` → `ValidateSongs` は通す。

`DeduplicateSongs` は AI が既にまとめた後でも残してある。開始時刻が離れていれば
別の歌唱として残るので取りこぼしは増えず、AI が見落とした重複を拾う安全網になる。

### **辞書は AI 経路では使わない**（構造フィルタだけ通す）

`FilterSongsWith` には 2 種類の判定が入っている。**AI 経路へ渡すのは構造のほうだけ**
（`filterScopeForPath`）：

| 判定 | 中身 | grouped / two_stage | regex |
|---|---|---|---|
| 構造フィルタ | 実況メモ・絵文字マーカー・罫線の注釈など、**形で**曲でないと分かるもの | 通す | 通す |
| 辞書（`filterKW` / `keepKW`） | 「オープニング」「待機」などの語で落とす | **使わない** | 使う |

**AI は既に `is_song` を判断している。** そこへ語の一致で落とす層を重ねると、
曲名がたまたま除外語と一致しただけの曲が消える。実際 `Week End` という曲が
`end` に当たって消えていた（issue #11、PR #13）。regex 経路には判断する者がいないので、
そちらだけ辞書を残す。

**抽出規則を変えたら `comment.RulesVersion` を上げること。** `comment_songs` は
`comment_raw` の hash でキャッシュされるので、規則だけ変えても既存の配信は
再解析されない。version を hash の計算に混ぜてあるので、上げれば
comment / chapter 両方のキャッシュが一斉に**失効する**。

> ⚠️ **失効するだけで、作り直しは自動では走らない。** `GET` も一覧も解析しないので、
> 放っておけば古い結果が残り続ける。`BackfillCommentSongsHashes` は監査専用で書き込まない。
>
> **comment と chapter で作り直す手段が違う。**
>
> | | 作り直す経路 |
> |---|---|
> | `comment_songs` | `batch-analyze`。**ただし全件ではない**（下記）／対話の `/comments/analyze` |
> | `chapter_songs` | **一括で全件を回す経路が無い**。`batch-fill` が `AnalyzeChaptersForBatch` を呼ぶのは Holodex もコメントも空の配信だけ。`POST /api/chapters/backfill` は `chapter_raw` を取るだけで再抽出しない。確実なのは配信ごとの `/chapters/analyze` |
>
> **`batch-analyze` も「全件」ではない。** 既定（`{}`）は未処理かつ表示中のみ。
> 最大範囲の `{"mode":"reanalyze","hidden":"all"}` でも、対象は
> **`comment_raw` が非空の JSON 配列**の行だけ（`refresh` は raw 条件を外す代わりに
> `is_processed = FALSE` に限られる）。したがって
> **処理済みで `comment_songs` はあるが `comment_raw` が NULL / `[]`** の配信は、
> version を上げて一括を流しても古いまま残る。そこは配信ごとの
> `/comments/analyze`（遠隔取得へ進む）でしか直せない。
>
> つまり現状、**comment 側にも chapter 側にも完全な一括再構築口は無い**。
>
> `songmatch.RulesVersion` は同じ「version を混ぜる」手だが、**効き方が違う**。
> あちらは起動時の再構築を前提にしているのに production では走っていない（issue #21）。

## 退避経路：2 段階（抽出 → 正規化）

統合経路が失敗したときの退避先。また、**元コメントが無い場面では今もこちらが本線**
（Holodex 由来の曲、編集画面の手動「AI 正規化」ボタン、読み仮名の補完）。

### 抽出（`ParseCommentsWithAI`）

入力行数と**同数**の要素を返させる。曲でない行も `is_song:false` で省略させない
（省略を許すと行番号がずれるため）。

```json
[
  {"line":1,"is_song":true,"start_ts":"9:26","end_ts":"","name":"さよなら、花泥棒さん","artist":""},
  {"line":2,"is_song":false,"start_ts":"1:14:47","end_ts":"","name":"","artist":""}
]
```

### 正規化（`BatchAINormalization`）

1 配信ぶんの曲を 1 回でまとめて処理する。渡すのは**抽出後の名前とアーティストだけ**で、
元のコメント行は渡していない。

```
以下の楽曲リストを処理してください：

[0] 楽曲名: さよなら、花泥棒さん
[5] 楽曲名: Part of your world / アーティスト: 英
[8] 楽曲名: 愛・おぼえていますか / アーティスト: アカペラ
```

```json
[{"index":0,"normalized_name":"愛・おぼえていますか","normalized_name_reading":"あいおぼえていますか",
  "original_artist":"飯島真理","original_artist_reading":"いいじままり",
  "tags":["acappella"],"confidence":0.9}]
```

> ⚠️ 上の入力例の `アーティスト: アカペラ` と `アーティスト: 英` は**誤り**。
> この経路の構造的な弱点で、後述の「既知の問題」を参照。

### AI が失敗したときの出力（実採取）

プロバイダーが全滅しても API は 200 を返し、**DB 照合だけを行った劣化結果**を返す。
呼び出し側はこれをエラーではなく `warning` の有無で判断する。

```json
{
  "suggestions": [{"index":0,"normalized_name":"愛・おぼえていますか (アカペラ)",
    "normalized_name_reading":"","original_artist":"飯島真理","original_artist_reading":"",
    "tags":[],"confidence":0}],
  "warning": "AI正規化に失敗しました（provider \"OpenAI\": API error: status=429 ...）。DB照合のみ実行しました。"
}
```

劣化の特徴：**名前は素通し**、**読みは空**、**タグは空**、`confidence` は 0。

## モデル差への対応（`pkg/ai`）

「OpenAI 互換」を名乗っていても細部は揃っていない。毎回コードを直すのではなく、
400 の内容と `finish_reason` から**回避策を学習して `baseURL|model` ごとに記憶**する。
往復が増えるのはプロセス起動後の最初の 1 回だけ。

gpt-5.6-luna への切り替えで実際に出た 3 つ：

| 症状 | 回避策 |
|---|---|
| `max_tokens` 非対応（400） | `max_completion_tokens` で送り直す |
| `temperature` は既定値のみ（400） | `temperature` を送らない |
| 応答が空で `finish_reason=length` | **推論モデル**のため枠に内部推論ぶんが含まれる。枠を倍にして再送 |

3 つ目が要注意。`completion=1024`（＝設定した枠ちょうど）なのに本文が空、という形で出る。
出力の長さから見積もった枠では届かないので、截断を検知したら倍にしていく（上限 16 倍）。

### 出力枠の見積もり

`estimateMaxTokens()` は user メッセージ長 × 4（下限 1024・上限 8192）。
以前は固定 8192 だった。課金は実出力ぶんなので金額には影響しないが、多くのプロバイダーは
レート制限を予約分込みで計算するため、無料枠が実使用の数倍の速さで枯れていた。

## 費用（GPT-5.6 Luna：入力 $0.20 / キャッシュ入力 $0.02 / 出力 $1.20 per 1M）

### 実測（配信 `hVfDBfreYNI`、候補 10 行 / 10 曲）

| 経路 | prompt | completion | 1 配信 |
|---|---:|---:|---:|
| 統合（1 回） | 1,595 | 1,022 | $0.00155 |
| 2 段階（抽出 1,181+386 / 正規化 1,004+976） | 2,185 | 1,362 | $0.00207 |

### ベンチマーク 20 配信での推算

| 経路 | 20 件 | 1,275 件 |
|---|---:|---:|
| 2 段階 | — | 約 $4.2（正規化ぶん込み） |
| 統合（combined：重複排除なし） | $0.075 | $4.75 |
| **統合（grouped：重複排除あり）** | **$0.047** | **$3.02** |

**費用は選定の決め手にならない**（全庫を丸ごと解析し直しても $3 前後）。品質で決めること。

### 費用構造で押さえておくこと

- **出力が支配的**。単価が入力の 6 倍なので、削るなら出力から
- 統合しても、非歌唱行に空フィールドを持たせると 2 段階より**高くなる**
  （実測で平均 18 行中 4 行が非歌唱行）。grouped が歌唱行だけを返すのはこのため
- プロンプトキャッシュの恩恵は小さい（約 7%）。入力自体が安いため。
  なお 2 段階の system prompt は 892 / 773 トークンで、よくある 1024 トークンの
  キャッシュの下限に届かない。統合版は 1,143 トークンで超える

## ベンチマーク

`cmd/setoribench` が ground truth（人手で確定した歌唱記録）と突き合わせて
precision / recall を出す。

```bash
go run ./cmd/setoribench -mode ai       -cache /tmp/bench-ai.json
go run ./cmd/setoribench -mode combined -cache /tmp/bench-combined.json
go run ./cmd/setoribench -mode grouped  -cache /tmp/bench-grouped.json
```

⚠️ キャッシュは stream ID だけをキーにしている。**モードごとに別のパスを渡すこと。**
プロンプトを変えて測り直すときも同じで、前の版の結果を読むと
「変えたのに何も変わらない」ように見える。

抽出だけでなく**照合も測れる**（`-match`、既定 on）。詳細は
[`SONG_MATCHING.md`](./SONG_MATCHING.md#継続して測るcmdsetoribench--match)。
非曲の雑音は `performances` が無い雑談配信に偏っていて GT では測れないので、
`-ids` で対象を名指しし `-nogt` / `-extractdump` で中身を見る。

### 2026-08-07 の結果（20 配信 / GT 247 曲、gpt-5.6-luna）

| mode | precision | recall | 抽出 | FP | FN |
|---|---:|---:|---:|---:|---:|
| ai（2 段階） | 0.992 | 0.996 | 248 | 2 | 1 |
| combined | 0.992 | 0.996 | 248 | 2 | 1 |
| **grouped** | **1.000** | 0.992 | 245 | **0** | 2 |

grouped は誤検出が 0 になった（`SWEET MEMORIES` と `メリッサ` の 2 件が消えた）。
複数コメントを突き合わせられるぶん雑音を排除できている。

> **combined と ai の数値が同一なのは、このベンチが抽出のみを評価するため。**
> combined が加える正規化とタグは測れておらず、両者の優劣はこの表からは判断できない。

計測上の注意：`-mode ai` は抽出しか呼ばないため、費用も抽出ぶんだけ。
production の 2 段階は正規化の呼び出しが別途要る。

## 照合が決着しないときの AI（補助）

規則で決められなかったものだけを AI に回す。詳細は [`SONG_MATCHING.md`](./SONG_MATCHING.md)。

### いつ呼ぶか

判定が走るのは**入力元を取り込むとき**。対話の「読み込む」だけでなく、
**一括セットリスト作成（`batch-fill`）も呼ぶ** ── あちらは歌唱を作るので、
決まらない行を人の審査へ回す前に AI に当てる必要がある。

| | AI 判定 | 理由 |
|---|---|---|
| 対話の analyze 3 端点 | ○ | 利用者が取り込みを指示している |
| **一括セットリスト作成**（`batch-fill`） | ○ | 歌唱を作る。審査へ回す前に決められるものは決める |
| **一括プレ分析**（`AnalyzeCommentsForBatch`） | × | 抽出は 1 回で済むのに AI が増える。誰も見ていない配信のために焚かない |
| 配信詳細の `GET`・一覧 | × | 閲覧者が通るだけの経路。見ているだけで AI を呼ぶことになる |
| `?dry_run=true` | × | 判定は checks テーブルへの書き込みを伴う |

**判定の結果は保存されない（肯定は）。** 残るのは否定
（曲は `song_identity_checks`、歌手の別人判定は `artist_alias_checks`）だけで、
肯定は応答に載るだけ。保存前に照合結果を落とす（コメント経路は `stripMatchForStorage`、
Holodex 経路は `stripMatchFromSuggestions`）。

したがって**「一度誰かが読み込めば以後は無料」ではない**。同じ配信で analyze を
もう一度押せば、キャッシュ命中でも未決着の行は再び AI に当たる（`adjudicateAll` は
cache hit の経路からも呼ばれる）。肯定を持ち越すのは、その場で歌唱を保存したときと、
`batch-fill` が歌唱または審査提案を作ったときだけ。

> **一度も動いていなかった時期がある。** 2026-08-07 に既定を統合経路へ切り替え、
> 翌 08-08 に別名義の判定を `BatchAINormalization` の中へ追加した。統合経路は
> そこを通らないので、追加した時点から実行されていなかった（本番の
> `artist_alias_checks` が 0 件だった理由）。既定の経路を変えたら、
> その経路に何が乗っていないかを確かめること。

### ①② 照合の判定（自動・`internal/service/match_ai.go`）

「どの曲か」と「歌手は同一人物か」を **1 回の呼び出しで**答えさせる。
AI は曲を選ぶ時点で両方の歌手名を見ているので、分けて聞くのは往復が増えるだけ。

二段構えで、どちらを使うかは候補の数で決まる（実測は `SONG_MATCHING.md`）。

**候補あり** … 候補だけを見せる。実測 212 行で 209 正解（98.6%）・誤答 0。

```
次の各行について、候補の中に同じ曲があればその id を、無ければ null を返してください。

0. 曲名「ひこうき雲」 アーティスト「松任谷由実」
   - 8f3c…|ひこうき雲|荒井由実
```

**候補ゼロ** … 楽曲カタログ全体を見せる。実測 43 行で 33 正解（76.7%）・誤答 0。
候補法はここを構造的に解けない（候補の中に答えが無い）。

```
登録済みの楽曲一覧（形式 id|曲名|アーティスト）:
s1|Rumor|Police Piccadilly
…（820 行）

0. 曲名「ルーマー」 アーティスト「ポリスピカデリー」
```

```json
[{"i":0,"id":"s1","conf":0.95,"why":"英日表記の違い","same_artist":true}]
```

- **判定の軸は「編曲が同じか」。** カバー・歌ってみたでも編曲が原曲と同じなら同一曲
  （誰が歌ったかは `performances` に記録するので `songs` の行は原曲を指す）
- 「少しでも確信が持てないなら null」をプロンプトで明示。null は新曲になるだけだが、
  誤って結び付けると歌唱が別の曲にぶら下がったまま気づけない
- `same_artist` は 3 値。true は**申し送るだけ**で、`artists.aliases` に入るのは
  人が編集フォームで保存したときだけ。false は `artist_alias_checks` に否定として残る。
  **連名は申し送らない**（どの名前どうしが同じ人か定まらない）
- **行番号は呼び出しごとに 0 起算**にし、範囲外は捨てる。通し番号にすると、モデルが
  バッチ内で振り直したときに別のバッチの答えを上書きする ── しかも応答は正常な形なので
  気づけない（実測で 8 行すべて正解のバッチが丸ごと誤答になった）。バッチ幅は 8
- 楽曲カタログはスナップショットで渡す。一括処理では開始時に一度だけ作る
  （prefix cache に載り、その回に自分が作った新曲を次の行の照合相手にしない）

### ③ 同名楽曲の重複判定（手動・`internal/service/song_dup_ai.go`）

「統合すべきか」は**聞かない**。実データでは同名の組に少なくとも 3 通りの正解がある。

```
惑星ループ（Eve / ナユタン星人）      artist 欄が原曲歌手と作曲者のどちらを記録したかの違い → 統合
翼をください（赤い鳥 / 桜高軽音部）    同じ作曲だが編曲が大きく違う             → 分けたまま
オレンジ（SPYAIR / 逢坂大河ほか）      そもそも別の曲                           → 分けたまま
```

「どれだけ違えば分けるか」は編集方針でデータからも AI からも出てこない。
一方「同じ作曲か」「編曲は同系統か」は公開された事実なので、そこだけ答えさせる。

```json
[{"i":0,"same_composition":true,"same_arrangement":false,
  "role_a":"『けいおん！』版・バンドアレンジ","role_b":"赤い鳥による原曲",
  "recommendation":"keep_separate","why":"同じ曲だが原曲とバンド編成が異なる"}]
```

実測（本番 DB の 3 組、gpt-5.6-luna）は 3 組とも意図どおりの判定だった。

- `recommendation` は `same_composition` / `same_arrangement` から機械的に決まる規則を
  プロンプトで指定している。AI の裁量にすると閾値がぶれる
- **知らない曲は `same_composition` を null にして「情報が無い」と書かせる。**
  推測で埋められると、判断材料が無いことに気づけない
- 判定理由（`why`）と各曲の立ち位置（`role_a` / `role_b`）は必ず UI に出す。
  マイナーな曲では AI がもっともらしい誤情報を生成するので、説明が不自然かどうかが唯一の防御線になる
- 判定は候補行に保存され、却下した組は行が残るので再走査で蒸し返されない

## 既知の問題

### 1. 2 段階経路では括弧内のバージョン表記がアーティスト名になる

```
入力    : 1:46:35 『愛・おぼえていますか』（アカペラ）
AI 出力 : {"name":"愛・おぼえていますか","artist":""}      ← AI は正しい
```

原因は AI ではなく Go 側。`ParseComment()` が baseline として括弧内をアーティストと解釈し、

結果として `acappella` タグが付かず（全 DB で 0 件だった）、アーティスト欄に無意味な値が入る。
実測：原文にバージョン表記を含む 38 件のうち 16 件（42%）で名前側から表記が失われていた。

**統合経路では解消済み**（AI が元のコメント行を見たまま判断できるため）。
ただし `ParseComment()` の baseline 自体は直っていないので、2 段階へ退避したときは再発する（TODO 19）。

> 一度は「タグ判定を正規表現で確定的に行う」案を採ろうとしたが、実データで却下した。
> バージョン表記の 51.8% は括弧を使わない裸の形（`幾億光年 piano ver./ Omoinotake`）で、
> さらに `リバベレ「ファタール」shorts公開!` の `shorts` のように語が現れていても
> 版種ではない例がある。判定には文脈の理解が要る。

### 2. ~~`max_tokens` が固定 8,192~~（2026-08-07 修正済み）

上の「出力枠の見積もり」を参照。

### 3. ~~`CleanJSONResponse` が正しい JSON 配列を壊していた~~（修正済み）

`[{...}]` のように**正しく `[` で始まる**応答で、先頭の `[` を削っていた。
条件が「`[` の位置が 0 より後か」だったため位置 0 では満たさず、直後の `{` の位置 1 で
切っていた。そのあと「`{` で始まるなら配列に包む」が働いて `]` が二重になる。

```
入力: [{"i":0,"same":true}]
出力: [{"i":0,"same":true}]]      ← json.Unmarshal が落ちる
```

**grouped 経路が無事だったのは `Decoder.Decode` が末尾の余りを無視するため。**
`json.Unmarshal` を使う別名義の判定だけが常に失敗していた。つまり判定を配線しても
AI の答えは毎回捨てられていた（実測で AI は `GUMI`/`グミ` を正しく判定できていた）。

同じ形の不具合を防ぐには、**応答の解析は `Unmarshal` で書く**のが安全
（`Decoder` は壊れた入力を黙って通す）。

## 失敗の扱い（無言で劣化させない）

このパイプラインは何度か「AI が失敗したのに成功に見える」形で事故を起こしている。
いずれも同じ構図なので、対策を明記しておく。

**起きたこと**（2026-08-07、モデル切り替え時の 400 エラー）：
抽出が失敗 → 正規表現へ退避 → 正規表現は 0 曲 → API は `{songs:[], warning:""}` を返す。
「この配信には曲が無い」という見た目で通り、**その空の結果がキャッシュに保存されて
既存の 10 曲を上書きした**。

**現在の防御**：

| 状況 | 扱い |
|---|---|
| AI 抽出が失敗して正規表現へ退避 | `warning` を返す。**キャッシュに書かない** |
| AI 正規化が失敗（劣化結果） | `warning` を返す。**キャッシュに書かない** |
| 統合経路が要素を返したのに 1 つも使えない | エラーにして 2 段階経路へ退避 |
| 統合経路が空配列を返した | 正常な結果として扱う（曲が無い配信もある） |
| タイムスタンプ行が 1 つも無い | 正常。警告もキャッシュ抑止もしない |

キャッシュに書かない理由は 2 つ。既存の良い結果を上書きしないため、そして
次回以降キャッシュ命中で AI を呼ばなくなり**劣化が固定される**のを防ぐため。

一括解析（`BatchAnalyzeService`）は `warning` の付いた配信を「失敗」として数え、
冷却を挟んで再試行する。

### 分析中にコメントが差し替わったら結果を捨てる（CAS）

分析は AI を挟むので数秒〜数十秒かかる。その間に Holodex 同期やコメント再取得が
`comment_raw` を差し替えると、無条件に書けば
**「raw は新しい内容、`comment_songs` と hash は古い入力から作ったもの」**が残る。
次の分析で hash が合わずに作り直されるので永続的な破損にはならないが、
それまでの間、その組み合わせを読む経路は hash を確認しない。

（PR #6 以降、一覧・検索は解析結果を常に省略し、詳細も `content:edit` のときだけ載せる。
なので古い結果が見えるのは編集権限付きの詳細など内部キャッシュを読む経路に限られる。
それでも編集画面が古い抽出を掴むので、ガード自体は要る。）

`SaveCommentSongs` は分析に使ったコメントを受け取り、
`comment_raw IS NOT DISTINCT FROM` がまだ一致するときだけ書く
（JSONB の意味的比較なので、正規化による表記の差では誤って捨てない）。

**「書けなかった」と「競合した」は別物なので、返し方も分けてある。**

- repository … 競合（0 行更新）は `(false, nil)`。DB エラーは `error`
- service … `CommentService.analyzeComments` は **`(false, nil)` のときだけ**
  `ErrCommentRawChanged` へ変換する。DB エラーは従来どおり警告ログのみで、
  呼び出し元へは伝えない

つまり下の 3 経路が反応するのは**競合だけ**で、書き込み失敗全般ではない。

**このエラーを扱う経路は 3 つある。足したときは全部見ること。**

| 経路 | 扱い |
|---|---|
| 一括プレ分析 | 冷却を挟まず即座に読み直す（90 秒の冷却は AI 劣化用） |
| 一括セットリスト作成 | 一度読み直し、二度目の競合ではその配信ごと諦めて `Skipped` |
| 対話型 `/comments/analyze` | 409。500 だとやり直せば通ることが伝わらない |

一括セットリスト作成で**「コメントが無い」と同じ扱いにしてはいけない**。
空のまま先へ進むと、Holodex に曲が無ければチャプターへ落ち、曲があっても
コメント固有の差分を丸ごと落とした、別ソースだけのセットリストを作る。

ログだけにするのも駄目で、一括は「err なし・warning なし」を成功条件にしているため
`done` に数えて再試行しない ── 完了表示の裏でキャッシュが空のまま残る。
