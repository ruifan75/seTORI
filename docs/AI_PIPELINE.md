# AI 解析パイプライン：入出力フォーマット

コメントから歌唱記録を起こすまでに AI を呼ぶのは **2 回だけ**（抽出・正規化）。
チャットの拍手から曲の終了時間を検出する処理（`pkg/chatend`）は純粋な文字列ロジックで、AI は使わない。

このドキュメントの実例は、すべて**実際の稼働ログから採取したもの**（2026-08-07、配信 `hVfDBfreYNI`）。
再取得するには `PUT /api/logs/level {"level":"DEBUG"}` にしてから
`POST /api/streams/{id}/comments/analyze?force=true` を叩き、ログの
`AI comment input` / `AI comment raw response` / `AI normalization input` を見る。

```
comment_raw（生コメント）
   │
   │  ① 前フィルタ：タイムスタンプを含む行だけ残す（Go・正規表現）
   ▼
   │  ② AI 呼び出し 1：抽出（どの行が曲か＋原文どおりの曲名/アーティスト）
   ▼
   │  ③ Go の確定的パース（時刻計算・逐語チェック）
   ▼
   │  ④ AI 呼び出し 2：正規化（表記ゆれ・読み・バージョンタグ）
   ▼
   │  ⑤ DB 照合 → comment_songs へ保存
```

---

## ① 前フィルタ（AI 呼び出し前）

`extractTimestampLines()` がタイムスタンプらしき文字列を含む行だけを残す。
**これがトークン量を決める最大の要因**で、生コメント全体を送ることはない。

実測（コメントを持つ 845 配信）：

| | 中央値 | 平均 | p90 | 最大 |
|---|---:|---:|---:|---:|
| 残る行数 | 14 行 | 18 行 | 43 行 | 99 行 |
| 送信文字数 | 390 字 | 528 字 | 1,364 字 | 3,694 字 |

---

## ② AI 呼び出し 1：抽出

`pkg/comment/ai_parser.go` の `ParseCommentsWithAI()`。

**役割の分担**が設計の要点：AI は「どの行が曲か」「原文のどこが時刻・曲名・アーティストか」を
**指し示すだけ**で、秒数への変換や妥当性検証は Go 側が確定的に行う。
AI が返した曲名・アーティストは、**元の行に逐語で存在する場合のみ**採用される（`isVerbatim`）。
幻覚による書き換えを構造的に防ぐため。

### 入力

- system prompt：固定 1,668 字（`commentAISystemPrompt`）
- user message：行番号を振った候補行

```
以下のコメント行をすべて解析してください。入力は 10 行です。各行について is_song を判定し、
**10 要素**を含む純粋なJSON配列のみを返してください（行の省略禁止）。

1) 9:26 『さよなら、花泥棒さん』
2) 20:42 『群青』
3) 32:30 『秒針を噛む』
4) 45:43 『Climax Jump』
5) 1:01:21 『君の知らない物語』
6) 1:15:19 『Part of your world』（英）
7) 1:23:12 『独りんぼエンヴィー』
8) 1:30:48 『夜明けと蛍』
9) 1:46:35 『愛・おぼえていますか』（アカペラ）
10) 2:02:43 『透明人間』
```

### 出力

入力行数と**同数**の要素を持つ JSON 配列。曲でない行も省略せず `is_song:false` で返させる
（省略を許すと行番号がずれるため）。

```json
[
  {"line":1,"is_song":true,"start_ts":"9:26","end_ts":"","name":"さよなら、花泥棒さん","artist":""},
  {"line":2,"is_song":true,"start_ts":"20:42","end_ts":"","name":"群青","artist":""},
  {"line":6,"is_song":true,"start_ts":"1:15:19","end_ts":"","name":"Part of your world","artist":""},
  {"line":9,"is_song":true,"start_ts":"1:46:35","end_ts":"","name":"愛・おぼえていますか","artist":""},
  {"line":10,"is_song":true,"start_ts":"2:02:43","end_ts":"","name":"透明人間","artist":""}
]
```

| フィールド | 意味 |
|---|---|
| `line` | 入力の行番号（1 始まり）。欠番不可 |
| `is_song` | 歌唱行なら true。雑談・開演/終了・スパチャ読み・感想などは false |
| `start_ts` / `end_ts` | **原文に書かれている時刻文字列をそのままコピー**。秒への変換は Go 側 |
| `name` / `artist` | 原文に逐語で現れる文字列のみ。翻訳・補完・並べ替えは禁止 |

曲でない行の例（`is_song:false` のときは name / artist は空文字列）：

```json
{"line":1,"is_song":false,"start_ts":"1:14:47","end_ts":"","name":"","artist":""}
```

---

## ③ Go の確定的パース（AI 呼び出しの間）

AI の返した選択をそのまま信じるのではなく、まず `ParseComment(originalLine)` を
baseline として走らせ、その上に AI の指摘を**条件付きで**重ねる。

- `start_ts` / `end_ts` は `parseTimestampString()` で秒に変換して上書き
- `name` / `artist` は逐語チェックを通った場合のみ上書き
- **空文字列は上書きしない** → baseline の値が残る

最後の挙動が後述の既知の問題につながる。

---

## ④ AI 呼び出し 2：正規化

`internal/service/normalization_service.go` の `BatchAINormalization()`。
1 配信ぶんの曲を **1 回の呼び出しでまとめて**処理する。

### 入力

- system prompt：固定 1,446 字（`batchSystemPrompt`）
- user message：`buildBatchMessage()` が組み立てる

```
以下の楽曲リストを処理してください：

[0] 楽曲名: さよなら、花泥棒さん
[1] 楽曲名: 群青
[5] 楽曲名: Part of your world / アーティスト: 英
[8] 楽曲名: 愛・おぼえていますか / アーティスト: アカペラ
[9] 楽曲名: 透明人間
```

> ⚠️ 渡すのは**抽出後の名前とアーティストだけ**で、元のコメント行は渡していない。
> 抽出段階で失われた情報はここでは復元できない。

### 出力

```json
[
  {
    "index": 0,
    "normalized_name": "愛・おぼえていますか",
    "normalized_name_reading": "あいおぼえていますか",
    "original_artist": "飯島真理",
    "original_artist_reading": "いいじままり",
    "tags": ["acappella"],
    "confidence": 0.9
  }
]
```

| フィールド | 意味 |
|---|---|
| `index` | 入力の番号（0 始まり） |
| `normalized_name` | 演奏バージョン表記を除いた曲名。ただし Remix / Cover / Live は別曲なので保持する |
| `*_reading` | 平仮名の読み |
| `tags` | 下記 7 種のみ。**原曲名の文字列から判定させている** |
| `confidence` | 0.0–1.0 |

使えるタグは 7 種に固定：
`acoustic` / `piano` / `弾き語り` / `acappella` / `short` / `full` / `medley`

### AI が失敗したときの出力（実採取）

プロバイダーが全滅しても API は 200 を返し、**DB 照合だけを行った劣化結果**を返す。
呼び出し側はこれをエラーではなく `warning` の有無で判断する。

```json
{
  "suggestions": [
    {
      "index": 0,
      "normalized_name": "愛・おぼえていますか (アカペラ)",
      "normalized_name_reading": "",
      "original_artist": "飯島真理",
      "original_artist_reading": "",
      "tags": [],
      "confidence": 0,
      "reasoning": ""
    }
  ],
  "warning": "AI正規化に失敗しました（provider \"OpenRouter\": API error: status=429 ...）。DB照合のみ実行しました。"
}
```

劣化の特徴：**名前は素通し**（正規化されない）、**読みは空**、**タグは空**、`confidence` は 0。
一括解析ではこの `warning` が付いた配信を「失敗」として数える。

## トークン量と費用の目安

上記の実測から積み上げた 1 配信あたりの概算（日英混在で約 1.87 字/token として較正）：

| | 入力 | 出力 | 合計 |
|---|---:|---:|---:|
| 中央値 | 2,088 | 1,144 | 3,232 |
| 平均 | 2,245 | 1,505 | 3,750 |
| p90 | 3,036 | 3,492 | 6,528 |
| 最大 | 5,224 | 8,198 | 13,421 |

入力の 6 割は 2 つの system prompt（固定 3,114 字）が占める。

全 1,275 配信を解析し直した場合の概算は、$0.15/$0.60 級のモデルで約 $1.6、
$3/$15 級でも約 $37。**費用は選定の決め手にならないので、品質で選ぶべき**。
候補モデルの比較には `cmd/setoribench`（ground truth と突き合わせて precision/recall を出す）を使う。

## 既知の問題

### 1. 括弧内のバージョン表記がアーティスト名になる

上の実例の 6 行目・9 行目がそれ：

```
入力    : 1:46:35 『愛・おぼえていますか』（アカペラ）
AI 出力 : {"name":"愛・おぼえていますか","artist":""}      ← AI は正しい
正規化へ: 楽曲名: 愛・おぼえていますか / アーティスト: アカペラ   ← 誤り
```

原因は AI ではなく Go 側。`ParseComment()` が baseline として括弧内を
アーティストと解釈し、AI が返した空文字列は上書きしないため baseline が残る。

結果として、
- `acappella` タグが付かない（正規化は**原曲名**からタグを判定するが、名前側には既に残っていない）
- アーティスト欄に「アカペラ」「英」といった無意味な値が入る

実測：原文にバージョン表記を含む 38 件のうち 16 件（42%）で名前側から表記が失われている。
全 DB で `acappella` タグが付いた歌唱記録は 0 件。

**対策の方針**：タグ判定を AI に任せず、`pkg/comment` 側で**元のコメント行**に対して
確定的に行う。正規化 prompt のタグ定義（「原曲名に Piano を含む」等）は本質的に
キーワード一致であり、AI を使う必要がない。抽出処理が
「AI は形式認識、計算と安全性は Go」という方針を採っているのと同じ理由。

### 2. `max_tokens` が固定 8,192

`pkg/ai/groq.go` の `MaxTokens: 8192` は固定値。**課金額には影響しない**（実出力ぶんの課金）が、
多くのプロバイダーはレート制限の計算に予約分を含めるため、**無料枠の消費が実使用の数倍になる**。

実例：Groq の 429 メッセージ `Used 93233, Requested 9263` のうち 8,192 が予約分。
実際の出力は中央値 1,144 トークン。入力行数から見積もる動的な値にすれば、
無料枠で処理できる件数は数倍になる。
