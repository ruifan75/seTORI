# セットリストを埋める流れ（単体編集と一括）

歌唱記録（`performances`）をどう作るか。入口は 2 つあり、**同じ照合の仕組みを通す**。

- **単体編集** … 人が配信を開き、入力元を選んで編集フォームに読み込み、確認して保存する
- **一括** … チャンネル範囲を選んで自動で埋める。確信が持てないものは人の審査に回す

この文書は 2026-08-12 に決めた設計。実装は段階的に入れる（末尾に状況）。

## 共通の前提

### 照合は保存しない、読み込みのときだけ計算する

`comment_songs` は**源**であって、答えを貼って回る場所ではない。
配信を開いただけの `GET /api/streams/{id}` も一覧も照合しない。
照合が走るのは**入力元を取り込む操作**で、対話（編集フォームへ読み込む）と
一括の両方にある：

| 端点 | 規則照合 | AI 判定 |
|---|---|---|
| `POST /api/streams/{id}/comments/analyze` | ○ | ○ |
| `POST /api/streams/{id}/holodex-songs/analyze` | ○ | ○ |
| `POST /api/streams/{id}/chapters/analyze` | ○ | ○ |
| `POST /api/streams/batch-analyze` | ○ | **×**（下記） |
| `POST /api/streams/batch-fill` | ○ | ○ |
| `GET /api/streams/{id}`・一覧 | × | × |

**一括プレ分析（batch-analyze）は AI の照合判定を呼ばない。** `AnalyzeCommentsForBatch` は
抽出まで（キャッシュ命中ならそれも飛ばす）で、規則照合は表示のために当たるが、
決まらない行を AI へ回すのは**取り込むとき**＝ batch-fill と対話の analyze だけ。
`comment_songs` へ保存する前に `stripMatchForStorage` が照合結果を落とすので、
保存されるのは抽出・正規化・拍手 end だけ、という約束は変わらない。

理由は `SONG_MATCHING.md` の「照合は保存しない」に書いた通りで、
保存すると曲が増えるたび・統合するたびに古くなり、それを追いかける仕組みが要る。

### 照合の段取り

```
① 規則で引く（SQL・数ミリ秒）      … 曲名キー → アーティストで検証
② 未照合なら AI に回す（match_ai） … 候補あり → 候補、候補ゼロ → 楽曲カタログ全体
③ それでも決まらなければ人へ
```

②の詳細と実測は `SONG_MATCHING.md`。誤答 0 で 94.9% が②までで決まる。

## 単体編集の流れ

```
① 人が「Holodex から読み込む」/「コメントから読み込む」を押す
② Holodex → AI 正規化を走らせる
   コメント → 走らせない（comment_songs に正規化済みの結果がある）
      ただし未解析なら、そこで抽出＋正規化を実行する
③ 規則で照合（matched / unmatched に分かれる）
④ unmatched を AI へ。候補があれば候補、無ければ楽曲カタログ全体。
   歌手が DB と違う場合は「同一人物か」も同じ呼び出しで聞く
⑤ 全曲を編集フォームへ。3 種類が混ざる：
     - 規則で照合できたもの
     - AI が照合したもの（曲名・歌手が書き換わっている場合がある）
     - どちらでも決まらなかったもの（新曲として登録される候補）
```

### AI が書き換えた欄には、元の値と理由と確信度を出す

`FieldChange`（`by` / `from` / `to` / `reason` / `score`）として応答に載せ、
`FieldProvenance` が曲名・歌手名の下に表示する。

```
曲名  深昏睡 (Deep coma)
      ← 深昏睡（AI 判定 95%：副題の表記違い）
```

**未記入 → 補完も記録する。** 落とすと、画面に理由なく歌手名が現れたように見える。

### 歌手の別名義はチェックボックスで、保存のときだけ入る

AI が `same_artist=true` を返したら `artist_alias` として申し送る。フォームには
「松任谷由実 を 荒井由実 の別名義として登録する」というチェックボックスを出す。

- **AI が同一人物と言った場合だけ既定でチェックが入る**
- 作曲者と原曲歌手の取り違え（`メルト / 初音ミク` に対し DB は `ryo (supercell)`）は
  「同じ曲だが別人」なのでチェックは入らない。本番ではこちらが多い
- 連名（`May'n & 中島愛`）は申し送り自体をしない
- 登録は保存時。別名義は**その人の全楽曲に効く**ので、読み込んだだけでは書かない
- 権限が無い人も提案として出せる。`POST /api/artists/aliases` が権限を見て振り分ける
  （あれば即時反映、無ければ `artists.aliases` への `field` 提案として積む）。
  対象は `artists` の行なので、曲を 1 つも持たない名義は提案できず 404 になる

## 一括の流れ

```
① 範囲（全部 / 複数チャンネル）と対象（未処理のみ / 全部 force）を選んで実行
② 各配信を自動で読み込む。入力元は Holodex 優先（正規化を走らせる）、
   無ければコメント（正規化は走らせない）
③ 規則で照合
④ unmatched を AI へ（単体編集と同じ二段構え）
⑤ 行き先を 3 つに分ける
     - 照合できた             → performances を作る
     - AI が高確信で照合した   → performances を作る（監査できる形で）
     - 決まらない / 条件に該当 → 人の審査へ
```

### 秘匿された配信に歌唱を作ってよくなった

一括は `FindStreamsForFill` で**非表示を除いたまま**（雑談・ゲーム配信を対象にしないため）。
以前ここを非表示込みにできなかったのは、`is_hidden` が発見面しか止めないので
**作った瞬間に未ログインから読めた**から。

PR #19（issue #4）で `streams.is_restricted` が入り、**実効的に秘匿された配信**の歌唱は
`content:edit` にしか返らなくなった。会限の歌枠は migration 052/053 で旗が立っている。

> ⚠️ **`is_hidden = true` は `is_restricted = true` を意味しない。**
> 秘匿の旗は availability / Holodex topic / `members_only` タグという**候補**から立てたもので、
> 非表示の全体を覆う不変条件ではない。実測（1307 本）：
>
> | | 秘匿でない | 秘匿 |
> |---|---:|---:|
> | 表示 | 583 | 1 |
> | **非表示** | **638** | 85 |
>
> つまり**非表示のうち 638 本は秘匿されていない**。ここへ一括を広げて歌唱を作ると、
> `PublicAccess` の `FindByStreamID` がそれを返し、匿名の配信詳細から読める。
> 広げてよいのは**既に実効的に秘匿されている行だけ**で、「非表示だから安全」ではない。

読み書きの内訳は `docs/STREAM_VISIBILITY.md`。一括は `EditorAccess` で既存の歌唱を読む
（秘匿された配信も編集対象になりうるため）。

### 3 つ目の入力元：配信者が付けたチャプター

Holodex にも曲が無く、コメントも取れない配信がある。本番相当のデータ（599 本）で 47 本。
そのうち **20 本にチャプターがあり、14 本は `曲名 / アーティスト` が並ぶ完全な歌単**
（約 138 曲）だった。残りは 1 章節だけ（`START`）や企画の区切りで、曲は取れない。

```
0:00    開始                          ← 曲でない章節は抽出が落とす
1:42    幕明け
2:07    ヴィーナスとジーザス / やくしまるえつこ
11:59   プラチナ / 坂本真綾
…
53:10   異端なスター / official髭男dism
59:07   閉幕
```

**抽出はコメントと同じ関数を通す**（`CommentService.ExtractSongs`）。章節を 1 通の
コメントに組み直して渡すだけで、「どの行が曲か」の判断・除外キーワード・AI が落ちた
ときの退避が全部そのまま効く。区切り文字で切ろうとすると
`ヨワネハキ / MAISONdes / feat. 和ぬか, asmi` や `I LOVE... / Official髭男dism / (音量注意）`
で崩れるので、判断は既に調整済みのところへ寄せる。

**一括での優先順位は最後**（Holodex → コメント → チャプター）。表記は配信者本人が
書いたもので信用できるが、章節の区切りは「その曲の場面」であって歌唱そのものではない
（曲のあとの MC を含む）。Holodex の iTunes ID もコメントの明示 end も捨ててまで
採る理由が無いので、**他に拾えるものが無い配信の受け皿**に留める。
拾った行は全部審査へ回す（`chapter_only`）── 章節から曲を切り出したのは AI の判定なので、
コメントにしか無い行を自動で作らないのと同じ扱いにする。

**end は `next_start` 扱い。** yt-dlp が返す章節の `end_time` は次の章節の開始そのもので、
`comment`（投稿者が明示した終了時刻）と同格に置くと確度での絞り込みが嘘になる。
拍手検出が上書きしたぶんだけ `chat` になる ── 実測した配信では 7 曲すべてが
拍手で埋まったので、実際に残るのは live chat が無い配信だけ。

**取得は yt-dlp**（`--print "%(chapters)j"`）。YouTube Data API は章節を返さず、
説明欄を自力で解析すると企画の時刻表（`19:00 ▹ …`）まで拾ってしまう。
一括の中では**呼ばない**（1 本あたり数秒かかる）ので、先に
`POST /api/chapters/backfill?concurrency=N` で `chapter_raw` を埋めておく。
`chapter_raw` は 3 態あり、**NULL（まだ調べていない）と `[]`（調べたが章節が無い）を
区別する** ── 同じにすると毎回全配信を取り直すか、取得を試す導線が消えるかのどちらかになる。

### Holodex を優先する理由と、優先しない場合

Holodex の曲は **iTunes ID を持っている**。これは最も強い証拠で、曲名が食い違っていても
照合できる（`深昏睡／Deep Coma` と `深昏睡 (Deep coma)`）。

ただし Holodex のセットリストは欠けていることがある。**数を比べるのではなく、時間で
1 曲ずつ突き合わせる。** Holodex 側に対応が無いコメントの行は拾って審査へ回す
（`comment_only`）。コメント抽出には誤検出があるので**自動では作らない**。

以前は曲数の比（1.5 倍以上かつ 3 曲以上の差）で「取りこぼしの疑い」を出していたが、
それでは 5 曲 vs 6 曲が素通りする。実際 `6SOyUVuOq9k` は Holodex 5 曲・コメント 6 曲で、
コメントにしか無い `Snow halation` が提案にも歌唱にもならずに消えていた。
**1 曲だけ足りない（最後の曲の登録漏れ）が Holodex の欠け方として一番多い**ので、
比率の門で守るのは的が外れていた。

### 必ず人の審査に回すもの

| 条件 | 理由 | 本番での量（465 配信 / 5432 行） |
|---|---|---|
| end time が**確かでない** | 終了時刻の推定は当たらないことがある | 130 行（2.4%）＋推定値 |
| 歌手が書かれていない | AI に歌手を推測させない方針（`AI_PIPELINE.md`） | 125 行（2.3%） |
| 照合できない | 新曲を無審査で作らない | 約 7% |
| 配信に歌手が複数いる | 誰が歌ったかを埋められない | 111 配信（24%） |
| force 実行で既存と食い違う | 既にある記録を黙って書き換えない | — |
| 同じ実行の中で同じ曲が重なる | 入力元に重複がある（一意制約は完全一致しか止めない） | — |

**判定は「値があるか」ではなく「その値が信用できるか」で行う。** 素朴に書くと
どちらも審査を素通りする：

- `no_end` … `end <= start` ではなく **`end_source` の確度**で見る。
  `next_start`（次の曲の開始で埋めた推定値）や `default`（240 秒）は
  「終了時間がある」とは言えない。以前はここを値の有無で見ていたので、
  推定で埋まった行がそのまま確定していた
- `no_artist` … 照合の**後**の歌手名ではなく**入力元から抽出したままの表記**で見る。
  照合が DB の楽曲から歌手名を補うので、後で見ると「歌手が書かれている」ことになり、
  「AI に歌手を推測させない」という方針が審査の手前で骨抜きになる

複数歌手の配信は参加者を並べてチェックさせる。**全行が審査対象になる**ので、
一括の主な待ち行列はここになる。

### 審査は修正提案の仕組みに乗せる

`perf.missing`（未登録曲の追加報告）として積む。自動反映の条件は
「異なるログインユーザーが N 人以上」なので、一括が作った提案は 1 つの出所しか持たず、
**自動では反映されない**（`suggestion_auto_apply` の設計がそのまま歯止めになる）。

#### 提案は照合の結果ごと運ぶ

`MissingSongPayload` には曲名・歌手・開始・終了に加えて、**`song_id`（照合済みの曲）**・
`singer_ids`・`end_source`・候補・AI の理由と確信度・どの実行が積んだかを載せる。

`song_id` を持たせるのが要点。持たせる前は承認が `findOrCreateSong` で
**曲名から引き直していた**ので、一括が決めた照合が承認の瞬間に捨てられ、
DB の表記と食い違う組（`深昏睡` ↔ `深昏睡 (Deep coma)`）では新曲が作られていた。
承認は `song_id` を優先し、無いときだけ引き直す。

#### 同じ行を二度積まない

`(配信, 開始秒 ±30, 曲名キー)` が一致する `perf.missing` が既にあれば作らない。
**却下済みも含めて見る** ── 却下を覚える先がここしかないので、処理済みを除くと
「却下したものが次の実行でまた出る」が直らない。

そのぶん**却下には持続する副作用がある**ので、取り消す口を用意してある
（`/admin/suggestions` の「却下」タブ →「却下を取り消す」、
`POST /api/suggestions/{id}/undo-rejection`）。提案の行を消し、「この曲ではない」を
押していれば `song_identity_checks` の否決も一緒に消す。取り消せないと、一度の
誤操作がその行を永久に沈めることになる ── 却下を覚えさせるなら、忘れさせる方法も要る。
対象は `perf.missing` の却下だけ。`field` / `perf.meta` の却下は次の提案を妨げないので、
消しても履歴が減るだけで得るものが無い。

### 審査は修正提案の画面（`/admin/suggestions`）で行う

**専用の画面は作らない。** 一度分けかけたが、次の 2 つの理由で 1 画面に戻した。

- **どの提案も再生して確かめる必要がある。** 一括の待ち行列だけでなく、時間のズレの
  報告もそうだった ── 自動反映は「2 人以上が 3 秒以内で一致」した分を先に片付けるので、
  **人手に残るのは佐証が取れなかった提案だけ**（1 人だけ・匿名・値が割れた）。
  つまり値を見比べても決まらないものばかりで、結局は録画を見ることになる。
  曲・アーティストの修正も同じで、曲名や原曲アーティストの当否は「編曲が同じか」で
  決まる（`SONG_MATCHING.md`）＝耳で判断する話。しかも 1 件の提案が曲名と読みを
  同時に触れるので、欄ごとに画面を振り分けることもできない
- **分組の軸が既に合っていた。** `perf.missing` は `target_key` に動画 ID を入れているので、
  対象ごとの分組（`ListGroupedByTarget`）がそのまま「配信ごと」になる

分けると `adopt`（1 件採用＋同項目の他案を却下）・まとめて反映の中央値・自動反映の設定・
衝突警示を作り直すことになり、そちらの方が壊すものが多い。既にある画面に
**プレイヤーとカードを足す**方を選んだ。

代わりに種別で絞れるようにした（すべて／セットリスト追加／内容の修正／曲の差し替え）。
一括は一度に数百件積むので、絞りが無いと利用者から届いた提案がその中に埋もれる。

#### プレイヤーは一度に 1 つだけ

対象の行の「▶ 再生」で開く。**同時に 1 つしか開かない** ── YT プレイヤーの参照は
`youtubePlayerControl` にグローバルで 1 つしか無く、複数開くと「今の再生位置を取り込む」が
最後に載った別の動画を指す。一覧を開いただけで何十本も動画を読み込まない利点もある。

再生元は対象の種類ごとに違う：

| 対象 | 何を再生するか |
|---|---|
| `stream`（＝`perf.missing`） | その配信。参加者と既存セットリストも並べる |
| `performance` | その歌唱の配信を開き、開始秒へ飛ぶ |
| `song` | 歌唱履歴から 1 つ選んで聴く（どれでも同じ曲なので最新を使う） |
| `artist` | 未対応。アーティストから歌唱を辿る経路がまだ無い |

未登録曲の追加を含む組だけは最初から開く。それ以外は畳んだまま
（値を見比べるだけの提案を素早く流し見る作業を、動画の読み込みで邪魔しないため）。

#### `perf.missing` の行は編集できるカードで出す

1 件のカードでできること：

- 再生位置へ飛ぶ／今の再生位置を開始・終了として取り込む／±1 秒の微調整
- 候補ボタンで曲を確定、検索して選び直し、照合を解除して新曲として登録
- 曲名・歌手名の直接編集（入力元の表記と AI の理由を横に出す）
- 配信の参加者を並べてチェック（**承認時に `SetSingers` まで通る**）
- 却下、または「この曲ではない」＝ `song_identity_checks` に否決を記録して却下

承認は編集内容を添えた 1 往復（`POST /api/suggestions/{id}/approve` に payload）。
時間を人が直した場合、`end_source` は `manual` になる ── 据え置くと拍手検出の値として
保存され、確度での絞り込みが嘘になる。

### 既にセットリストがある配信には書き足さない

`CreatePerformances` はセットリスト**全体**を受け取って差分を取る。書き足すには既存分も
送り直すことになり、その過程で既存の歌唱が曲名から引き直される（別の曲に付け替わりうる）。

人が作ったものを機械の都合で作り直さない。既存がある配信では、追加したい曲も
`perf.missing` の提案として出す。

### 自動で作った歌唱は、まとめて取り消せること

一括は `performances` に直接書く。書いた以上、後から**その回の分だけ**戻せる必要がある。

- `batch_fill_runs`（実行 1 回）と `performances.batch_run_id` を持つ
- `created_via` … 規則で照合 / AI が照合 のどちらで作られたか
- `match_confidence` … AI の確信度

これが無いと、誤った実行の後始末が「数千件から手で探す」になる。

### AI への問い合わせはチャンネルを跨いでまとめる

楽曲カタログ（約 820 曲・12k トークン）は毎回同じで、変わるのは行だけ。
配信ごとに呼ぶと楽曲カタログを配信の数だけ送ることになる。

- 実行の開始時に楽曲カタログのスナップショットを 1 つ作る
- 候補ゼロの行を**実行全体から集め、表記で重複を除いてから** 8〜10 行ずつ問う
- 楽曲カタログは問いの先頭に置く（prefix cache に載る）

本番の実測（356 配信）で言うと、候補ゼロは 82 行・65 種・58 配信。
配信ごとなら 58 回、まとめれば **9 回**で済む。

## 起きうる場面と、そのときどうなるか

実装しながら確かめた分類。**「黙って書かない」「消さない」「決めきれないものは人へ」**の
3 つが通底していて、迷ったら人に回す側へ倒す。

### 入力元の選び方

| 場面 | どうなるか |
|---|---|
| Holodex とコメントの両方に曲がある | Holodex を採る（曲ごとに iTunes ID を持つ＝最も強い証拠） |
| Holodex に無く、コメントにだけある曲がある | その行だけを拾って審査へ（`comment_only`）。Holodex 側は通常どおり処理する |
| Holodex に曲が無い | コメントを使う |
| Holodex にもコメントにも曲が無く、チャプターがある | チャプターから拾い、**全行を審査へ**（`chapter_only`） |
| どこにも曲が無く `comment_raw` も `chapter_raw` も無い | そもそも対象に含まれない（`FindStreamsForFill`） |
| チャプターが未取得（`chapter_raw` が NULL） | 対象に含まれない。yt-dlp は一括の中では呼ばないので、先に backfill する |
| コメントが未解析（`comment_raw` だけある） | 対象に含める。読み込みの側が抽出から走らせる（AI）。一括では判定は行わず、抽出だけ |
| `comment_songs` が JSON の `null` | 対象から外れる。`jsonb_typeof = 'array'` で守っている（ここを素で書いて実行が即死した） |

### 照合の結果ごと

| 場面 | 例 | どうなるか |
|---|---|---|
| 規則で 0.85 以上 | `ギラギラ / Ado` が文字列で完全一致 | そのまま作成。`created_via=rule`、確信度 1.00 |
| 曲名は一致・歌手が未記入（`title_only` 0.80） | `宿命` だけ書かれている | 自動採用の水準に届かない → AI へ。**歌手未記入は別途審査行き**なので結局人が見る |
| 曲名は一致・歌手が違う（`title_mismatch` 0.6） | `ルージュの伝言 / 松任谷由実` ↔ DB `荒井由実` | AI が同じ曲と判定すれば採用。同一人物かも同時に答えるが、**一括では別名義を登録しない**（人の確認を経ていないため。単体編集のチェックボックスだけが登録経路） |
| 同じ曲・別人 | `メルト / 初音ミク` ↔ DB `ryo (supercell)` | 曲は採用。「別人」は否定として記録し、次から同じ提案をしない |
| 編曲違いで別の曲 | `翼をください / 桜高軽音部` ↔ DB `赤い鳥` | AI が null → 未照合 → 審査へ。**新曲を勝手に作らない** |
| 候補ゼロだが DB にはある | `Rumor / Police Piccadilly` → `ルーマー / ポリスピカデリー` | 楽曲カタログ全体への問い合わせで解ける → 採用 |
| 候補ゼロで DB にも無い | `Real Face / KAT-TUN` | AI が null → 審査へ（`perf.missing` として積む） |
| AI が答えたが確信度が足りない | 0.85 未満 | 採用しない → 審査へ（`low_conf`） |
| 過去に人が「別の曲」と否決した組 | — | 候補から外れ、AI にも聞かない（`song_identity_checks` の否定） |
| 同じ表記が複数の配信に出る | `革命道中` が 7 配信 | AI へは**1 回だけ**聞き、答えを全配信に反映する |
| AI が落ちている | 全プロバイダー冷却など | 規則の結果のまま進み、未照合は審査へ。誤ったものを書くことはない |

### 時間・歌手まわり

| 場面 | どうなるか |
|---|---|
| 終了時間が無い、または推定値でしかない | 審査へ（`no_end`）。判定は `end_source` の確度で行う |
| 終了時間が推定値 | 作成はするが `end_source = next_start`・`end_confirmed = false` で残る。確度の低い行として後から絞り込める |
| どの由来で作られたか知りたい | `end_source` は**確度**（chat / holodex / comment …）、`created_via` は**誰が決めたか**（rule / ai）。混ぜないこと ── 一時 `end_source = "batch"` と書いていて、拍手検出や Holodex 明示という確度の情報が消えていた |
| 拍手検出の値が入っている | `end_source = chat` として作成 |
| Holodex が明示している | `end_source = holodex` |
| 歌手が書かれていない | 審査へ（`no_artist`）。**抽出時の表記**で見る（照合が補った値では見ない） |
| 配信に歌手が 1 人 | その人を歌手として作成 |
| 配信に歌手が複数 | **全行を審査へ**（`multi_singer`）。誰が歌ったかは機械では決められない |
| 参加者が取れない（DB エラー等） | 複数扱いにする（安全側＝人に見せる） |

### 既にセットリストがある配信

**比べるのは歌唱として比較できる要素すべて**（曲・開始・終了）。曲 ID だけを見ていた頃は、
開始が何十秒ずれていても「同じ」として黙って飛ばしていた。入力元による数秒の揺れは日常なので
3 秒までは同じとみなし、終了は入力元が確かな値を持っているときだけ比べる。

| 場面 | どうなるか |
|---|---|
| `unprocessed` モード | そもそも対象外（歌唱が 1 つも無い配信だけを見る） |
| `force` モード・曲も時間も一致（±3 秒） | 何もしない |
| `force` モード・同じ曲だが時間がずれる | 審査へ（`conflict`）。既存を書き換えない |
| `force` モード・時間が重なるが別の曲 | 審査へ（`conflict`）。既存を書き換えない |
| `force` モード・重ならない新しい曲 | 審査へ。**書き足さない** ── 追加するには既存分も送り直すことになり、その過程で既存の歌唱が曲名から引き直される（別の曲に付け替わりうる） |
| `force` モード・既存にあるが入力元に無い | **提案は作らず** `batch_fill_gaps` に残す（後述） |

> ⚠️ **ここの `conflict` は「審査理由」であって、提案の `status` ではない。**
> 同じ語が 2 つの意味で使われているので、対処も別になる。
>
> | | 何か | 付く先 | 承認したらどうなる |
> |---|---|---|---|
> | 一括の `reviewConflict` | **審査理由**（`review_reasons`） | `perf.missing` の通常の pending 提案 | **歌唱を新しく作る**。既存は書き換わらない（完全な重複なら作成が失敗し、許される重なりなら並んで増える） |
> | 提案の `status = conflict` | **状態**（提案後に対象が編集された） | `field` / 曲差し替え | `?force=1` で現在値を上書きして承認できる |
>
> **`?force=1` は前者に効かない。** `approveMissingSong` は `KindMissingSong` を
> 先に分岐して処理し、`force` を受け取らない。一括の食い違いを「既存を置き換える」
> つもりで force 承認すると、失敗するか別の歌唱が増える。
> 既存を直したいなら、審査画面で歌唱そのものを編集する。

### 実行そのもの

| 場面 | どうなるか |
|---|---|
| 実行中にもう一度開始 | 409（`ErrBatchFillAlreadyRunning`）。同時に 2 つは走らない |
| 停止を押した | 処理中の 1 件が終わり次第止まる。**それまでに書いた分は残る**（status=cancelled） |
| 撤回 | その実行が作った歌唱だけを消す。人が作った行は `batch_run_id` を持たないので無傷 |
| 審査の提案が大量に出る | seTORI 自身の投稿は絞り込みを飛ばす（`SuggestionActor.System`）。ここを素通りにしていて、審査へ回すはずの 303 行のうち 295 行が静かに消えた |
| 審査の提案が自動反映されないか | されない。自動反映は「異なるログインユーザーが N 人以上」が条件で、一括は出所が 1 つしか無い |

### 「DB にあるが入力元に無い」は審査に積まず、実行の付随情報として残す

`force` の突き合わせで出る 4 通りのうち、これだけ行き先が無かった。

**提案として積まない。** 源（Holodex のセットリストもコメントも）は欠けているのが普通なので、
欠落 1 件ごとに審査待ちを作ると人が処理できない量になる。しかも「入力元に無い」だけでは
何をすべきか決まらない ── 入力元の取りこぼしのこともあれば、登録が誤っていることもあり、
消すのが正しいとは限らない。審査待ちは「人が判断すれば決着する」ものだけを入れる場所で、
判断の材料が足りないものを積むと、待ち行列そのものが信用されなくなる。

**かといってログだけでは誰も気付けない。** `batch_fill_gaps`（実行 × 歌唱）に残し、
`batch_fill_runs.songs_gap` に件数を持たせて、管理→同期の実行履歴から内訳を開けるようにした。
自動では何もしない ── 見えるようにするところまでが役目。

歌唱が消えれば記録も消える（`ON DELETE CASCADE`）。この行は「その歌唱についての観察」なので、
対象が無くなったら残す意味が無い。件数と内訳が食い違うことがあるのはそのため。

### 撤回は人の編集を巻き込まない

一括が作った歌唱を人が編集した時点で **`batch_run_id` を外す**（`PerformanceRepository.Update`
と `ReconcilePerformances` の更新枝）。直した行はもう人のものなので、その実行を撤回しても
消えない。`created_via` / `match_confidence` は残す ── 「元は AI が作った行」という履歴まで
消す理由は無い。

一括が既存行を更新することは無い（歌唱がある配信には書き足さず審査へ回す）ので、
更新＝人の編集と見てよい。

### まだ手当てしていないもの

正直に残しておく。どれも「誤ったデータを書く」側ではなく「人の手間が増える」側の穴。

- **「この行はそもそも曲ではない」型の却下を覚える先が無い。** 曲の同一性の否決は
  `song_identity_checks` に残るが、抽出そのものの誤り（曲ではない行）は
  同じ提案の重複判定（同じ配信・開始秒・曲名キー）でしか止まらない。
  入力元の抽出が変わって表記が動くと、また出てくる
- **第 1 段が逐次。** 126 配信で 17 分（Holodex のキャッシュが無いと AI 正規化が走る）。
  並行にすれば縮むが、AI の同時実行数も一緒に増える

### 実行の範囲

- 対象チャンネルは**複数選べる**。空なら全チャンネル
- 既定は選んだチャンネルが**所有する**配信（`stream_singers.is_owner`）。
  以前は参加者で絞っていたので、あるチャンネルを選んだつもりが、そのチャンネルが
  ゲスト参加しただけの他人の配信まで対象になっていた
- 「ゲスト参加した配信も含む」を明示的に立てたときだけ、コラボ先まで広がる
