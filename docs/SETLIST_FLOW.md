# セットリストを埋める流れ（単体編集と一括）

歌唱記録（`performances`）をどう作るか。入口は 2 つあり、**同じ照合の仕組みを通す**。

- **単体編集** … 人が配信を開き、源を選んで編集フォームに読み込み、確認して保存する
- **一括** … チャンネル範囲を選んで自動で埋める。確信が持てないものは人の審査に回す

この文書は 2026-08-12 に決めた設計。実装は段階的に入れる（末尾に状況）。

## 共通の前提

### 照合は保存しない、読み込みのときだけ計算する

`comment_songs` は**源**であって、答えを貼って回る場所ではない。
配信を開いただけの `GET /api/streams/{id}` も一覧も照合しない。
照合が走るのは「どの源から取り込むかを決めて編集フォームへ読み込む」操作だけ：

| 端点 | 何をするか |
|---|---|
| `POST /api/streams/{id}/comments/analyze` | 抽出（キャッシュ）→ 照合 → AI 判定 |
| `POST /api/streams/{id}/holodex-songs/analyze` | 正規化 → 照合 → AI 判定 |

理由は `SONG_MATCHING.md` の「照合は保存しない」に書いた通りで、
保存すると曲が増えるたび・統合するたびに古くなり、それを追いかける仕組みが要る。

### 照合の段取り

```
① 規則で引く（SQL・数ミリ秒）      … 曲名キー → アーティストで検証
② 未照合なら AI に回す（match_ai） … 候補あり → 候補、候補ゼロ → 曲庫まるごと
③ それでも決まらなければ人へ
```

②の詳細と実測は `SONG_MATCHING.md`。誤答 0 で 94.9% が②までで決まる。

## 単体編集の流れ

```
① 人が「Holodex から読み込む」/「コメントから読み込む」を押す
② Holodex → AI 正規化を走らせる
   コメント → 走らせない（comment_songs に正規化済みの結果がある）
      ただし未解析なら、そこで抽出＋正規化を実行する
③ 規則で照合（matched / unmatched に分かれる）
④ unmatched を AI へ。候補があれば候補、無ければ曲庫まるごと。
   歌手が DB と違う場合は「同一人物か」も同じ呼び出しで聞く
⑤ 全曲を編集フォームへ。3 種類が混ざる：
     - 規則で照合できたもの
     - AI が照合したもの（曲名・歌手が書き換わっている場合がある）
     - どちらでも決まらなかったもの（新曲として登録される候補）
```

### AI が書き換えた欄には、元の値と理由と確信度を出す

`FieldChange`（`by` / `from` / `to` / `reason` / `score`）として応答に載せ、
`FieldProvenance` が曲名・歌手名の下に表示する。

```
曲名  深昏睡 (Deep coma)
      ← 深昏睡（AI 判定 95%：副題の表記違い）
```

**未記入 → 補完も記録する。** 落とすと、画面に理由なく歌手名が現れたように見える。

### 歌手の別名義はチェックボックスで、保存のときだけ入る

AI が `same_artist=true` を返したら `artist_alias` として申し送る。フォームには
「松任谷由実 を 荒井由実 の別名義として登録する」というチェックボックスを出す。

- **AI が同一人物と言った場合だけ既定でチェックが入る**
- 作曲者と原唱の取り違え（`メルト / 初音ミク` に対し DB は `ryo (supercell)`）は
  「同じ曲だが別人」なのでチェックは入らない。本番ではこちらが多い
- 連名（`May'n & 中島愛`）は申し送り自体をしない
- 登録は保存時。別名義は**その人の全楽曲に効く**ので、読み込んだだけでは書かない
- 権限が無い人も提案として出せる。`POST /api/artists/aliases` が権限を見て振り分ける
  （あれば即時反映、無ければ `artists.aliases` への `field` 提案として積む）。
  対象は `artists` の行なので、曲を 1 つも持たない名義は提案できず 404 になる

## 一括の流れ

```
① 範囲（全部 / 一部チャンネル）と対象（未処理のみ / 全部 force）を選んで実行
② 各配信を自動で読み込む。源は Holodex 優先（正規化を走らせる）、
   無ければコメント（正規化は走らせない）
③ 規則で照合
④ unmatched を AI へ（単体編集と同じ二段構え）
⑤ 行き先を 3 つに分ける
     - 照合できた             → performances を作る
     - AI が高確信で照合した   → performances を作る（監査できる形で）
     - 決まらない / 条件に該当 → 人の審査へ
```

### Holodex を優先する理由と、優先しない場合

Holodex の曲は **iTunes ID を持っている**。これは最も強い証拠で、曲名が食い違っていても
照合できる（`深昏睡／Deep Coma` と `深昏睡 (Deep coma)`）。

ただし Holodex のセットリストは欠けていることがある。**コメント側の曲数が明らかに多い場合は
その旨を出す**（黙って少ない方を採らない）。

### 必ず人の審査に回すもの

| 条件 | 理由 | 本番での量（465 配信 / 5432 行） |
|---|---|---|
| end time が無い | 終了時刻の推定は当たらないことがある | 130 行（2.4%） |
| 歌手が書かれていない | AI に歌手を推測させない方針（`AI_PIPELINE.md`） | 125 行（2.3%） |
| 照合できない | 新曲を無審査で作らない | 約 7% |
| 配信に歌手が複数いる | 誰が歌ったかを埋められない | 111 配信（24%） |
| force 実行で既存と食い違う | 既にある記録を黙って書き換えない | — |

複数歌手の配信は参加者を並べてチェックさせる。**全行が審査対象になる**ので、
一括の主な待ち行列はここになる。

### 審査は修正提案の仕組みに乗せる

`perf.missing`（未登録曲の追加報告）として積む。自動反映の条件は
「異なるログインユーザーが N 人以上」なので、一括が作った提案は 1 つの出所しか持たず、
**自動では反映されない**（`suggestion_auto_apply` の設計がそのまま歯止めになる）。

審査の画面は単体編集と同じ操作にする ── 再生して時間を確かめ、承認か却下を選ぶ。

### 既にセットリストがある配信には書き足さない

`CreatePerformances` はセットリスト**全体**を受け取って差分を取る。書き足すには既存分も
送り直すことになり、その過程で既存の歌唱が曲名から引き直される（別の曲に付け替わりうる）。

人が作ったものを機械の都合で作り直さない。既存がある配信では、追加したい曲も
`perf.missing` の提案として出す。

### 自動で作った歌唱は、まとめて取り消せること

一括は `performances` に直接書く。書いた以上、後から**その回の分だけ**戻せる必要がある。

- `batch_fill_runs`（実行 1 回）と `performances.batch_run_id` を持つ
- `created_via` … 規則で照合 / AI が照合 のどちらで作られたか
- `match_confidence` … AI の確信度

これが無いと、誤った実行の後始末が「数千件から手で探す」になる。

### AI への問い合わせはチャンネルを跨いでまとめる

曲庫（約 820 曲・12k トークン）は毎回同じで、変わるのは行だけ。
配信ごとに呼ぶと曲庫を配信の数だけ送ることになる。

- 実行の開始時に曲庫のスナップショットを 1 つ作る
- 候補ゼロの行を**実行全体から集め、表記で重複を除いてから** 8〜10 行ずつ問う
- 曲庫は問いの先頭に置く（prefix cache に載る）

本番の実測（356 配信）で言うと、候補ゼロは 82 行・65 種・58 配信。
配信ごとなら 58 回、まとめれば **9 回**で済む。

## 起きうる場面と、そのときどうなるか

実装しながら確かめた分類。**「黙って書かない」「消さない」「決めきれないものは人へ」**の
3 つが通底していて、迷ったら人に回す側へ倒す。

### 源の選び方

| 場面 | どうなるか |
|---|---|
| Holodex とコメントの両方に曲がある | Holodex を採る（曲ごとに iTunes ID を持つ＝最も強い証拠） |
| Holodex の方が明らかに少ない（コメントが 1.5 倍以上かつ 3 曲以上多い） | Holodex を採るが**全行を審査へ**。取りこぼしを黙って確定させない |
| Holodex に曲が無い | コメントを使う |
| どちらにも曲が無い | そもそも対象に含まれない（`FindStreamsForFill`） |
| コメントが未解析 | 抽出から走る（AI）。一括では判定は行わず、抽出だけ |
| `comment_songs` が JSON の `null` | 対象から外れる。`jsonb_typeof = 'array'` で守っている（ここを素で書いて実行が即死した） |

### 照合の結果ごと

| 場面 | 例 | どうなるか |
|---|---|---|
| 規則で 0.85 以上 | `ギラギラ / Ado` が逐字一致 | そのまま作成。`created_via=rule`、確信度 1.00 |
| 曲名は一致・歌手が未記入（`title_only` 0.80） | `宿命` だけ書かれている | 自動採用の水準に届かない → AI へ。**歌手未記入は別途審査行き**なので結局人が見る |
| 曲名は一致・歌手が違う（`title_mismatch` 0.6） | `ルージュの伝言 / 松任谷由実` ↔ DB `荒井由実` | AI が同じ曲と判定すれば採用。同一人物かも同時に答えるが、**一括では別名義を登録しない**（人の確認を経ていないため。単体編集のチェックボックスだけが登録経路） |
| 同じ曲・別人 | `メルト / 初音ミク` ↔ DB `ryo (supercell)` | 曲は採用。「別人」は否定として記録し、次から同じ提案をしない |
| 編曲違いで別の曲 | `翼をください / 桜高軽音部` ↔ DB `赤い鳥` | AI が null → 未照合 → 審査へ。**新曲を勝手に作らない** |
| 候補ゼロだが DB にはある | `Rumor / Police Piccadilly` → `ルーマー / ポリスピカデリー` | 曲庫まるごとの問い合わせで解ける → 採用 |
| 候補ゼロで DB にも無い | `Real Face / KAT-TUN` | AI が null → 審査へ（`perf.missing` として積む） |
| AI が答えたが確信度が足りない | 0.85 未満 | 採用しない → 審査へ（`low_conf`） |
| 過去に人が「別の曲」と否決した組 | — | 候補から外れ、AI にも聞かない（`song_identity_checks` の否定） |
| 同じ表記が複数の配信に出る | `革命道中` が 7 配信 | AI へは**1 回だけ**聞き、答えを全配信に反映する |
| AI が落ちている | 全プロバイダー冷却など | 規則の結果のまま進み、未照合は審査へ。誤ったものを書くことはない |

### 時間・歌手まわり

| 場面 | どうなるか |
|---|---|
| 終了時間が無い（`end <= start`） | 審査へ（`no_end`） |
| 終了時間が推定値 | 作成はするが `end_source = next_start`・`end_confirmed = false` で残る。確度の低い行として後から絞り込める |
| どの由来で作られたか知りたい | `end_source` は**確度**（chat / holodex / comment …）、`created_via` は**誰が決めたか**（rule / ai）。混ぜないこと ── 一時 `end_source = "batch"` と書いていて、拍手検出や Holodex 明示という確度の情報が消えていた |
| 拍手検出の値が入っている | `end_source = chat` として作成 |
| Holodex が明示している | `end_source = holodex` |
| 歌手が書かれていない | 審査へ（`no_artist`）。**AI に歌手を推測させない**方針の帰結 |
| 配信に歌手が 1 人 | その人を歌手として作成 |
| 配信に歌手が複数 | **全行を審査へ**（`multi_singer`）。誰が歌ったかは機械では決められない |
| 参加者が取れない（DB エラー等） | 複数扱いにする（安全側＝人に見せる） |

### 既にセットリストがある配信

| 場面 | どうなるか |
|---|---|
| `unprocessed` モード | そもそも対象外（歌唱が 1 つも無い配信だけを見る） |
| `force` モード・時間が重なり同じ曲 | 何もしない |
| `force` モード・時間が重なるが別の曲 | 審査へ（`conflict`）。既存を書き換えない |
| `force` モード・重ならない新しい曲 | 審査へ。**書き足さない** ── 追加するには既存分も送り直すことになり、その過程で既存の歌唱が曲名から引き直される（別の曲に付け替わりうる） |

### 実行そのもの

| 場面 | どうなるか |
|---|---|
| 実行中にもう一度開始 | 409（`ErrBatchFillAlreadyRunning`）。同時に 2 つは走らない |
| 停止を押した | 処理中の 1 件が終わり次第止まる。**それまでに書いた分は残る**（status=cancelled） |
| 撤回 | その実行が作った歌唱だけを消す。人が作った行は `batch_run_id` を持たないので無傷 |
| 審査の提案が大量に出る | seTORI 自身の投稿は絞り込みを飛ばす（`SuggestionActor.System`）。ここを素通りにしていて、審査へ回すはずの 303 行のうち 295 行が静かに消えた |
| 審査の提案が自動反映されないか | されない。自動反映は「異なるログインユーザーが N 人以上」が条件で、一括は出所が 1 つしか無い |

### 審査の受け皿にはまだ穴がある（TODO 41）

`perf.missing` は「未登録曲の追加報告」であって、一括の審査待ちを運ぶために作った器では
ないので、いくつか落ちるものがある。**2 つはデータを壊す側**なので先に直す。

- 🔴 承認は曲を**文字列から引き直す**（`CreateFromMissingSong` → `findOrCreateSong`）。
  提案に `song_id` を持てないため、batch が既に決めた照合結果が承認の瞬間に捨てられる。
  DB の表記と食い違う組（`深昏睡` ↔ `深昏睡 (Deep coma)`）では新曲が作られる
- 🔴 承認で作った歌唱に**歌手が紐づかない**（`SetSingers` を呼んでいない）。
  `end_source` / `end_confirmed` も渡していない
- 🟡 同じ行の提案が何度でも積まれる（重複判定が無く、絞り込みも飛ばしている）
- 🟡 却下を覚えないので、次の実行でまた同じものが出る

### まだ手当てしていないもの

正直に残しておく。どれも「誤ったデータを書く」側ではなく「人の手間が増える」側の穴。

- **同じ実行の中での重複は見ていない。** 既存の歌唱とは 30 秒の窓で突き合わせるが、
  同じ配信の中に数秒ずれた同じ曲が 2 行あると 2 件できる
  （一意制約は `(stream_id, song_id, start_seconds)` なので完全一致しか止まらない）
- **撤回は人の編集を巻き込む。** 一括が作った行を人が直しても `batch_run_id` は残るので、
  その実行を撤回すると直した行も消える。人が編集した時点で `batch_run_id` を外す
  （＝もう人のもの）のが素直
- **第 1 段が逐次。** 126 配信で 17 分（Holodex のキャッシュが無いと AI 正規化が走る）。
  並行にすれば縮むが、AI の同時実行数も一緒に増える
